The recorded endpoints and statuses above are this project's own lane
evidence. The candidate explanation is a limitation Cursor users and staff
describe: in a Cursor forum thread, users report that the app's installation
page shows `Issues: Read and write` while the token minted for the sandbox
omits the `issues` scope, and Cursor staff describe that as a known
limitation and name a workaround, a `GH_TOKEN` secret in the Cloud Agent
settings
([forum thread, June–September 2026](https://forum.cursor.com/t/cloud-agent-gh-git-token-missing-issues-write-despite-github-app-being-granted-issues-read-write/163389)).
It is a hypothesis for this project, not a finding: this project's
installation page and the minted token were not inspected by the auditor
(owner-only), so a setting of this installation is not ruled out, and the
recorded `X-Accepted-GitHub-Permissions` values name the permission each
refused endpoint requires, not the permissions the token held, so they do not
distinguish the reported token limitation from an installation setting or
from another integration or proxy restriction. For this project the root
cause therefore stays reported, not confirmed; the refusals themselves are
confirmed. The installation's permissions page (owner action 4) can settle
only the first of these: if it lacks Issues write, that is the cause; if it
shows Issues read and write, the installation setting is ruled out and the
choice between the minted token and another integration or proxy restriction
still needs token or operation evidence, such as one issue comment attempted
with the installation token and its recorded status.
Whether that secret restores agent-driven writes is not established: the Codex
review of this record cites a 6 October staff reply that the secret
authenticates `gh` while the agent's instructions still treat it as read-only
for writes ([thread 173522](https://forum.cursor.com/t/cloud-agent-instructions-block-gh-writes-even-when-a-write-scoped-gh-token-is-provided/173522),
not opened by the auditor). The lanes' own workaround, recording the verdict by
editing the bot's acknowledgement comment and having another lane post board
records, is consistent with the cause and stays in force until a Cloud Agent's
new issue comment is observed to succeed; record the first such success here.
No lane reports a Cloud Agent run with the secret so far
([229/6042013379](https://github.com/d6g8k5htny-coder/main/issues/229#issuecomment-6042013379)).

ruleset's history, which the owner can read (Settings → Rules → Rulesets →
"Verified pull requests" → History) and lane credentials cannot (403). Both
documents carry a dated correction. Author-reported, head-associated check
observation: for every one
of the 62 pull requests merged into `main` since 30 September, the check runs
named `verify`, `public-intake` and `public-shop` that GitHub associates with

This does not bind those runs to the tested
merge commit that the required-check contract names, does not verify review

bypass was ever used is therefore not established from here, in either

that required hosted checks remain required at the tested commit for every
lane, so the auditor's recommendation is to remove the bypass. Recording it
here as an accepted exception is the alternative; either is the owner's

   access, include every project repository. This widens what the
   installation may reach, not necessarily what a Cloud Agent's token reaches:
   GitHub lets an app
   [restrict an installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)
   to a subset of the installation's repositories, and this record says the
   minted token is bound to the task repository. Cross-repository reads
   therefore stay UNKNOWN until a Cloud Agent reads one file from another
   project repository and reports it. Writes through the installation token
   are equally UNKNOWN after this change: a token minted without a repository
   restriction covers every repository in the installation, and the
   task-repository-only observation above cannot distinguish a restricted
   token from an installation that included only that repository. The same
   first run should therefore also attempt one pull-request comment on a
   second project repository and report both results with their
   authentication path, so that the widened installation's write scope is
   observed rather than assumed. Record the path actually selected, without
   disclosing token material, and the resulting GitHub principal, as separate
   facts. A comment that appears as `cursor[bot]` went through the
   installation token. An owner-attributed comment alone does not identify
   the credential: the `GH_TOKEN` of action 1 and an app's user-access token
   both post as the owner's user. `gh` prefers `GH_TOKEN` whenever that
   variable is set, so a run that has both must make the probe calls with the
   installation token explicitly; when the selected path cannot be
   established, installation-token scope stays UNKNOWN. A successful comment
   establishes that one operation, not every write. Writes through the
   `GH_TOKEN` of action 1, if honored, reach all four repositories.

## For every lane

- Report a refusal, do not route around it: the endpoint, the status, the
  `X-Accepted-GitHub-Permissions` value when present, and what you did instead.
  One line in the delivery comment is enough.
- Keep three things apart: the owner's authority, the tool or harness a lane
  actually has, and the operation observed. A granted token or a passing
  `gh auth` check is not capability evidence; a successful merge does not show
  that issue posting, cross-repository push or workflow dispatch works. Only
  an observed operation, labeled by operation, repository, runtime and time,
  is; anything uninspected stays UNKNOWN.
- Do not ask Dylan for permission the delegation already grants. Ask him only
  for the actions above, and only once they are not yet done.
- Cursor Cloud Agents, until a Cloud Agent's new issue comment is observed to
  succeed: record pickups and verdicts in the acknowledgement comment or on the
  pull request, and ask a lane that can write to the boards to post tip locks
  and board records, as the record already shows.
- Claude sessions: attach the project repositories at the start of the session,
  one call per repository. When the harness refuses something, classify the
  obstacle before routing any work around it. A denial of an action stays a
  denial whatever its wording and whichever operation exposed it: do not
  retry it, and do not have another session or lane perform that action in
  your place; hold the text for the owner, say so in the record, and carry on
  with unrelated authorized work. A tool that is absent, or a request shape
  the harness cannot make, is different: there, text that would have been
  posted may go to a lane that is authorized to publish it and is not itself
  under a denial for that action, with ownership of the work unchanged.
  Whether a refusal in another session would recur is not known from this
  record (see "Where the refusals come from"). If the scope of a denial is
  unclear, pause the affected action and ask for its exact scope; unrelated
  work continues.
- Never use a ruleset bypass, and never simulate another identity's approval.
