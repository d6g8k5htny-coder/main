The recorded endpoints and statuses above are this project's own lane
evidence. The explanation is Cursor's documented limitation, not a setting of
this installation: in a Cursor forum thread, users report that the app's
installation page shows `Issues: Read and write` while the token minted for
the sandbox omits the `issues` scope, and Cursor staff describe that as a known
limitation and name a workaround, a `GH_TOKEN` secret in the Cloud Agent
settings
([forum thread, June–September 2026](https://forum.cursor.com/t/cloud-agent-gh-git-token-missing-issues-write-despite-github-app-being-granted-issues-read-write/163389)).
This project's installation page and the minted token were not inspected by
the auditor (owner-only). The recorded `X-Accepted-GitHub-Permissions` values
name the permission each refused endpoint requires, not the permissions the
token held, so they do not distinguish the reported token limitation from
another integration or proxy restriction. For this project the root cause
therefore stays reported, not confirmed; the refusals themselves are confirmed.
Whether that secret restores agent-driven writes is not established: the Codex
review of this record cites a 6 October staff reply that the secret
authenticates `gh` while the agent's instructions still treat it as read-only
for writes ([thread 173522](https://forum.cursor.com/t/cloud-agent-instructions-block-gh-writes-even-when-a-write-scoped-gh-token-is-provided/173522),
not opened by the auditor). The lanes' own workaround, recording the verdict by
editing the bot's acknowledgement comment and having another lane post board
records, is consistent with the cause and stays in force until a Cloud Agent's
new issue comment is observed to succeed; record the first such success here.

The bypass exempts one lane from the pull-request requirement, the three
required checks, non-fast-forward and deletion protection on `main`.
[docs/FORMAL_REQUIRED_CHECKS.md](../docs/FORMAL_REQUIRED_CHECKS.md) described it
as "a pre-existing repository-role PR bypass"; the live actor is the
integration. Author-reported, head-associated check observation: for every one
of the 62 pull requests merged into `main` since 30 September, the check runs
named `verify`, `public-intake` and `public-shop` that GitHub associates with
the pull-request head were at `success` before the merge time (check-run API
read, 2026-10-07 16:30Z; the non-success `public-intake` runs on 34 of those
heads are `pull_request_target` re-runs that started after the merge), and
every first-parent commit is a pull-request merge whose tree equals the
mechanical merge of its parents. This does not bind those runs to the tested
merge commit that the required-check contract names, does not verify review
thread resolution at each merge time, and does not establish when the bypass
actor was added (ruleset history returns 403 to lane credentials). Whether the
bypass was ever used is therefore not established from here, in either
direction. The project's own rule is
that required hosted checks remain required at the tested commit for every
lane, so the auditor's recommendation is to remove the bypass. Recording it
here as an accepted exception is the alternative; either is the owner's
decision, and until it is recorded the choice is pending.

## For every lane

- Report a refusal, do not route around it: the endpoint, the status, the
  `X-Accepted-GitHub-Permissions` value when present, and what you did instead.
  One line in the delivery comment is enough.
- Keep three things apart: the owner's authority, the tool or harness a lane
  actually has, and the operation observed. A granted token or a passing
  `gh auth` check is not capability evidence; a successful merge does not show
  that issue posting, cross-repository push or workflow dispatch works. Only
  an observed operation, labeled by operation, repository, runtime and time,
  is; anything uninspected stays UNKNOWN.
- Do not ask Dylan for permission the delegation already grants. Ask him only
  for the actions above, and only once they are not yet done.
- Cursor Cloud Agents, until a Cloud Agent's new issue comment is observed to
  succeed: record pickups and verdicts in the acknowledgement comment or on the
  pull request, and ask a lane that can write to the boards to post tip locks
  and board records, as the record already shows.
- Claude sessions: attach the project repositories at the start of the session.
  If the harness refuses an attach or a credential read, work read-only, hold
  the text of any post, and hand it to a lane that can publish it.
- Never use a ruleset bypass, and never simulate another identity's approval.
