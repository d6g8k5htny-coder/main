108-excerpt dataset and raw payload in both versions. Four fresh browser contexts
per version alternate before/after order at 1200px and 390px, in both themes.
The baseline is immutable Main5596 code replayed after authoring; it is not a
claimed pre-authoring measurement timestamp.

| --- | ---: | ---: |

| Open evidence disclosure by keyboard | 7.8 ms | 12.3 ms |
| Activate 3D to first observed renderer frame | 291.8 ms | 305.9 ms |
| Decoded resource bytes before activating 3D | 2,158,310 | 2,165,372 |

All eight contexts rendered the complete 49-node/55-edge graph. Twenty measured
keyboard-to-frame observations per version range from 10.0–23.2ms before and
13.8–22.3ms after. Observed CPU render-submission time is 3.3–8.2ms before and
3.5–7.3ms after. These are browser-observed counters and CPU submission timings,
not GPU presentation time or a sustained frame-rate guarantee. Three.js remains
absent before activation; its existing decoded module is approximately 1.27MB.
Decoded sizes are not compressed network-transfer sizes. The refinement adds
7,062 decoded bytes before 3D activation.

This is a small sample on a shared Linux host using local HTTP, not evidence of
a speedup or a network performance guarantee. No larger-graph limit was measured;
the renderer's existing 150-node cap remains unchanged. Software rendering does
not qualify a physical mobile GPU.

Visual inspection confirms separated footer targets at 320px, visible gold
keyboard focus around the scrollable relationship list, and readable source
and declaration links in the phone viewport. The explicit arithmetic limitation
helps distinguish the companion calculation from the research theorem. Opening
every evidence disclosure still creates a long phone reading path; native
collapsed disclosures keep the initial claim view shorter. These are engineering
observations, not a human usability study. The next accessibility increment is
spoken screen-reader and physical touch qualification on supported devices.
