## Findings

**Critical: none found.**

**Important I1 — duplicate JSON node identities are silently collapsed before validation.** `docs/site/compare-model.mjs:118` and `:120` parse through ordinary `JSON.parse` (directly for schema2, via existing `parseVerifiedSnapshot` for schema1). A hash-matching payload containing two entries with the same node ID is admitted, with the earlier record silently discarded. The subsequent source/reference/excerpt uniqueness checks cannot recover duplicate object keys. This violates the explicit duplicate-ID refusal requirement and can produce a misleading literal comparison from malformed retained bytes. A tiny diagnostic injected a duplicate first node with a different classification into the actual current payload and recomputed its byte descriptor: `parsePayload` admitted it and displayed only the last classification; authoritative `tools/current_site_data.py:44` `parse_json` refused the exact same bytes with `duplicate JSON key`. Digest integrity is necessary but does not resolve ambiguous JSON. Add duplicate-key rejection before ordinary object decoding for admitted payloads, and a focused raw-byte regression covering duplicate node IDs. Apply equivalent protection to registry/metadata decoding where duplicate members could be hidden. Diagnostic bytes: `review-duplicate-node.json` beside this report.

**Important I2 — valid current/archive byte identity disables the entire viewer.** `docs/site/compare-model.mjs:192` rejects a current observation whenever its SHA equals any retained archive ID. For schema1, archive ID is the payload SHA, so publishing the same exact observation as the retained snapshot is a legitimate producer state, not ambiguous content. `validate_manifest` has no such exclusion. A diagnostic based on the actual registry, using its current archive's payload descriptor as the current observation and recomputing history accounting, passes authoritative `validate_manifest` but fails this viewer with `Ambiguous current and archive IDs.` All comparisons become unavailable, even between other archives. Distinguish selection identity from content identity (or explicitly coalesce identical content while preserving current/archive roles); do not reject an otherwise valid publication. Add a focused same-bytes current/archive case. Diagnostic registry: `review-identical-registry.json`.

**Minor M1 — an invalid share URL cannot recover through the offered selectors.** `docs/site/compare.mjs:220` runs URL selection validation before enabling Load at `:222`; its error leaves the selectors enabled but Load disabled. The selector change handler at `:239` changes the status to “Awaiting comparison… Load the selected observations” without enabling Load. Retry rereads the same invalid URL. A real-browser diagnostic opened `?from=forged&to=forged`, explicitly selected a valid option, and confirmed the awaiting message alongside `load_disabled: true`. Keep initial refusal, but permit a deliberate subsequent selection to replace the invalid URL through Load. This does not require a silent fallback. Diagnostic: `review-diagnostics.json`.

**Minor M2 — future schema2 selectors show the material archive ID, not the exact payload digest requested by the spec.** `docs/site/compare-model.mjs:172` sets choice ID to the archive ID for both versions; `docs/site/compare.mjs:213` and `:145` expose that value as the selection identity. For schema1 this happens to be the exact payload digest; for schema2 the producer's archive ID is `mathematical_digest`, which intentionally excludes observation time and selected pin/label fields, and differs from `current.json`'s SHA. Raw payload verification itself uses the correct descriptor. Label archive/material identity explicitly and expose `descriptor.sha256` plus byte count in the exact selection disclosure (and ideally the selector's accessible description), so readers can identify the exact compared bytes without reverse-engineering the registry. This is a display/spec issue, not a scientific judgement.
