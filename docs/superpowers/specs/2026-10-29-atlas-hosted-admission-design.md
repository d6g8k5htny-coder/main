# Atlas hosted rendering admission design

A useful 3D Atlas must keep working after future edits. Main4ef's existing
hosted/publication browser operator has39 cases, but none activates Atlas3D.
The separate spatial16 and recovery13 operators establish their release
observations only. A renderer or inspector-focus regression can therefore
survive that hosted admission path.

The owner delegated priorities, implementation and cooperation and explicitly
opted out of repeated permission questions. The following are author engineering
choices, not user-specified details. Current claim388/6501974017, board619.

## Approaches

1. Extend the existing hosted browser operator through a small reusable helper
   (chosen): the same checked/generated source and browser report acquire real
   canvas, picking and recovery evidence; existing workflows remain unchanged.
2. Keep running standalone release tools: useful diagnostics but leaves the
   continuing publication gap open.
3. Add another workflow: adds operational/permission surface without needing it.

## Scope and architecture

New tools/atlas_spatial_admission.py exports
exercise_spatial_admission(browser, origin, output, report, data, expect).
It appends bounded hosted-spatial-* cases, closes only its contexts and preserves
all existing cases. tools/current_site_browser_check.py calls it alongside its
existing helpers and supplies the actual source observation. The parent adds an
optional --browser executable selector for reproducible local operation; absent
that option, the existing CI packaged Chrome channel remains the default.

spatial release operator, with Chromium sandbox ALWAYS enabled. No dependency,
workflow, credential, protection, CSP, mathematical source, production UI or
scientific-status authority changes.
