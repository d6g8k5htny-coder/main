# Signed Lease and Write Boundary Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax. The present task creates this contract only; the proposed implementation and tests need separate active ownership and actual hosted RED.

**Goal:** Establish an authenticated, atomic, signed lease protocol, then prove that an enrolled publisher enforces its current fence at each actual Git or Work Events write. A signed grant, a cooperative claim, or a green CI check alone does not establish write exclusion.

**Architecture:** Start with a disposable hosted SQLite ledger, a pinned Ed25519 backend, and a controlled synthetic publisher. Keep grant issuance, durable write admission, native execution and native readback distinct. Evaluate a Sites/D1 service separately, then enroll real writers only where an exclusive outbound path and safe recovery can actually be demonstrated.

**Tech stack:** Python stdlib JSON/SQLite for the first mechanism, a separately pinned supported `cryptography` Ed25519 runtime, frozen public test vectors, multiprocess hosted controls, and append-only engineering receipts. A future Sites service would use prepared D1 statements and Workers Web Crypto, subject to compatibility and authentication tests.

## Review focus

1. A valid signature survives lease expiry, key rotation, process pause or reassignment. Every write needs authoritative current-state checks; offline signature verification establishes only signed bytes and trusted key lineage.
2. A caller can pass admission, pause, and later write after its lease expires. The publisher must hold a durable write reservation through execution and uncertainty; admission returned to a credential-bearing arbitrary client is insufficient.
3. A successful SQL statement can update zero rows. A D1 batch must not commit its idempotency/outbox rows when its CAS predicate lost. Failure must be proved transactional, not inferred from a subsequent read.
4. A timed-out native request can still apply later. Current unchanged state or zero matching rows alone cannot prove non-application or permit reassignment.
5. A normal merge, scheduled action, human editor, browser connector or another provider can bypass a cooperative broker. Production exclusion depends on actual writer enrollment and native restrictions, not on a signed policy document.

## Small first protocol and trusted interfaces

The first candidate is a library in `architecture/lease_protocol.py`, exercised only by external hosted controls in `tests/test_architecture_lease_protocol.py`. It has no network connector, Site, production credential or access to a real governing worksheet. A trusted test harness supplies an isolated DB path, public fixture signing keys, a configured resource registry and an explicitly synthetic authenticated context. Authentication injection in this fixture is not evidence for service authentication. Future HTTP/connector adapters and runtime-lock/receipt files need separate ownership; this task creates none of them.

The library interfaces are `acquire(request, trusted_context)`, `renew(grant, request, trusted_context)`, `release(grant, request, trusted_context)`, `begin_write(grant, intent, trusted_publisher_context)`, `record_outcome(reservation, native_outcome, trusted_publisher_context)`, `reconcile(reservation, reconciliation_evidence, trusted_recovery_context)`, and `verify_signature(envelope, trusted_public_bundle)`. Exact function/class spelling and fixture ABI must be frozen with the test author before publication. Inputs cannot select SQL identifiers, imports, arbitrary URLs, file paths or outbound credentials. A DB location and adapter registry are trusted construction arguments, never grant fields.

The service authenticates a principal and session outside request JSON and checks a server-owned authorization policy for the registered resource, operation and active claim. `holder_principal`, `holder_session`, `issuer_id`, keys, clock and policy digest come from that context or the durable server registry; echoing them in a packet cannot authenticate them. Resource IDs select exact server-owned native targets. Path aliases, case aliases, subtree overlap and branch/ref aliases must resolve to the same exclusion resource before a grant is possible. First production scope serializes one repository ref, or one Work Events worksheet append stream, rather than claiming independent file leases prevent ref-level races.

Requests are strict UTF-8 JSON, <=64KiB, <=16 container levels, with closed wrapper keys, duplicate keys/nonfinite values refused and exact scalar types. Identifiers are bounded ASCII strings without control characters; SHA-256 values are64 lowercase hex digits. IDs and hashes are validated before transactions or signing. Public errors contain a stable reason code and request ID, never private native payload, secret, traceback or key bytes. Synthetic tests retain their complete public packets; production audit retains payload hashes and existing source references under the governing privacy policy.

`Intent` binds `{schema_version, intent_id, resource_id, scope_id, operation_kind, native_target, expected_native, payload_sha256, source_sha256, claim_id}`. The immutable server registry checks the target and operation. `expected_native` carries the actual precondition, including expected branch head for a ref update; expected PR head and expected base head for a merge; or the approved append contract and unique event identity for Work Events. A field's presence does not mean the upstream API enforces it. Complete canonical intent bytes are hashed, and the publisher must construct the exact native request from the retained intent. An arbitrary body with the same display description is refused.

`GrantPayload` has exactly `{schema_version, issuer_id, issuer_epoch, key_id, resource_id, scope_id, holder_principal, holder_session, claim_id, source_sha256, generation, fence, revision, request_id, request_sha256, intent_id, intent_sha256, expected_native_sha256, issued_at_s, expires_at_s, authorization_policy_sha256, scientific_effect, scientific_status_authority}`. schema_version is1; generation and issuer_epoch are32 lowercase hex digits; fence and revision are canonical positive decimal strings without leading zeroes. request_sha256 binds the complete closed canonical issuance request, including its operation kind, rather than only the desired native payload; request_id binds its idempotency record. Scientific fields are exactly `NONE` and `false`. Each grant covers one immutable intent. Renewal preserves that intent and fence, increments revision, binds the renewal request and invalidates prior revisions for new write admission. A different intent needs a new grant after the previous operation is terminal.

Canonical signing bytes are ASCII JSON with sorted keys, compact separators, no floats, and no implicit coercion/normalization, prefixed by the exact bytes `research-lease/v1\0`. The envelope is exactly `{payload, signature_base64url}`, with unpadded canonical base64url encoding of a64-byte Ed25519 signature. The trusted public bundle selects key_id; a public key or issuer supplied only by the request is not a trust anchor. Cross-runtime fixture bytes must match exactly. This domain prefix uses ordinary Ed25519 over the prefixed message, not the separate Ed25519ctx/Ed25519ph variants. Use the supported library backend rather than copying RFC reference arithmetic. [RFC8032 algorithms and vectors](https://www.rfc-editor.org/rfc/rfc8032/), [cryptography Ed25519 API](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/).

## Ledger, time, idempotence and state transitions

SQLite uses a real write transaction beginning before the current resource/key/policy read. Resource update, fence allocation, immutable grant payload, idempotency result and pending audit/outbox record commit together. Return no positive grant before commit. Explicitly roll back on every failed predicate, signing error, constraint failure, busy result, disk/full or uncertain transaction completion; retain the failure and inspect committed state through a separate status operation. No automatic retry or active-lock manipulation occurs in the pilot. SQLite permits one writer and `BEGIN IMMEDIATE` can return busy; that documented behavior is a mechanism to measure, not permission to force another writer. [SQLite transactions](https://www.sqlite.org/lang_transaction.html).

The ledger contains a resource row, immutable grants, immutable intents, reservations/outcomes, idempotency results, key/policy status, append-only audit events and delivery outbox. Primary/unique constraints bind resource identity, generation, `(principal, request_id)`, and intent/reservation identity. Losing operations cannot produce a grant, consume a successful idempotency result, enqueue a success audit or mutate the synthetic target. Historical fence and grant rows are never deleted to make a takeover possible.

| State | Allowed transition | Mandatory condition |
| --- | --- | --- |
| AVAILABLE | acquire -> LEASED | No unresolved native operation or legacy ownership hold; exact current policy/claim authorized. Allocate prior fence+1 and new generation. |
| LEASED | renew -> LEASED | Same current holder/generation/fence/revision/intent, unexpired, no write reservation; increment revision without changing generation/fence. |
| LEASED | release or expiry -> AVAILABLE | No write reservation; retain historical counter and revoke old revision. Expiry is evaluated by the authoritative ledger. |
| LEASED | begin_write -> WRITE_INFLIGHT | Trusted enrolled publisher; valid signature and currently active key/policy; exact current grant/intent; unexpired; exact native precondition established by the adapter's actual boundary. Commit the reservation before any outbound call. |
| WRITE_INFLIGHT | record terminal outcome | Native terminal evidence plus required readback; outcome is APPLIED or DEFINITELY_NOT_APPLIED. Expiry cannot clear the reservation. |
| WRITE_INFLIGHT | timeout/crash/ambiguous response -> WRITE_UNKNOWN | Preserve reservation and original request identity; refuse acquire, renew, release, repeated send and takeover. |
| WRITE_UNKNOWN | reconcile -> terminal or RECONCILIATION_HOLD | Trusted native evidence identifies the effect and proves the old operation cannot subsequently apply; otherwise keep the hold. |
| Any nonterminal state | integrity/restore/authentication uncertainty -> RECONCILIATION_HOLD | No new write; retain the original state, evidence and recovery path. |

Terminal operation rows remain historical. Only a terminal operation permits the resource to become AVAILABLE and a later grant to allocate a higher fence. Reservations are broker-private records, not portable signed admission capabilities returned to an untrusted writer. A reservation binds the exact publisher identity, grant revision, operation bytes, native destination and delivery attempt. A duplicate `begin_write` returns status of the original reservation and cannot cause another send.

Fences/revisions are stored as checked SQLite signed integers up to2^63-1 and serialized as decimal strings, including D1 results, to avoid JavaScript precision loss. Refuse counter exhaustion; never wrap/reset/reuse a fence. First fixture TTL is120 seconds, allowed service TTL range30–300 seconds. The authoritative database/server clock supplies integer UNIX seconds; client timestamps and local verification time cannot extend validity. Persist a per-resource time high-water mark and hold on a backward clock observation. A test-only injected clock is visibly synthetic and unavailable in service request JSON. Forward jumps can expire an unreserved lease; they cannot release WRITE_INFLIGHT/WRITE_UNKNOWN. Measure clock behavior separately from signature verification.

Idempotency binds `(authenticated_principal, request_id)` to the canonical request SHA and original committed result. Identical replay returns the original bytes/status and never renews, extends expiry, increments a counter or reacquires an expired grant. The same ID with different bytes is refused. Querying status is distinct from resending an operation. Keep idempotency tombstones for the full admissible replay lifetime; v1 never silently evicts them. Storage exhaustion holds new admissions until resolved.

After restart, the committed ledger, current issuer epoch, key/policy state, outbox and unresolved reservations are reopened and checked before any grant. A lost response after commit is recoverable by its idempotency identity. A lost response before known commit remains uncertain until durable status is read. A backup restore cannot reuse old fences or simply invent a fresh epoch and declare outstanding native requests gone: reconcile/drain old writers and pending operations, prove a durable counter high-water mark, then start a new pinned epoch. If this evidence is unavailable, retain a hold.

## Signing keys and audit delivery

Prepare a stable supported Ed25519 runtime before product tests: freeze the exact Linux image digest, Python/SQLite/crypto package/wheel/shared-library identities and OpenSSL backend, platform/architecture, licenses and runtime import path. An upstream `latest` documentation URL is not a version pin. Dependencies are prepared in the trusted hosted stage and mounted read-only; the untrusted project cannot substitute packages through its working directory. Preserve normal/-O child interpreter propagation and use the same frozen dependency bytes. No stdlib-only Python Ed25519 claim, HMAC substitution or handwritten curve implementation is acceptable.

Service private keys belong only to the broker signing boundary, separate from existing sealed governance guidance, and never to browser code, clients, connector packets, receipts or repository fixtures. Public RFC fixture private keys are public test data and must be labeled nonproduction. Future production provisioning/rotation uses the platform's actual secret support under a separate task; this plan acquires or prints no secret. The public trust bundle binds issuer, epoch, bundle revision, key_id, public key, activation/retirement/revocation state and signature by a separately pinned root trust anchor. A request-provided self-signed bundle cannot replace that anchor.

Rotate issuance to a new active key without dropping historical public verification. Before each write check the live key status and policy/bundle revision in the same authority that owns the reservation. Revocation immediately blocks new admission under that key; it does not cancel an already sent native request or prove non-application. Tests must preserve a revoked historical signature as cryptographically verifiable while refusing it for live admission. A key update racing begin_write has one committed order; an admitted operation remains reserved through reconciliation. Recovery operations require narrower server-owned authority, not an ordinary holder's `force` field.

Each committed transition records a monotonically ordered engineering audit event and a deterministic outbox intent in the ledger. Append evidence through the existing Work Events procedure; never rewrite historical claims, outcomes or rows. Delivery states are PENDING, SENDING, UNKNOWN and ACKNOWLEDGED. Mark ACKNOWLEDGED only after native metadata and actual payload/reference readback agree, including the unique event ID and payload hash. Transport success alone is insufficient. A pending event can be sent once by an enrolled delivery writer; an unknown attempt is held rather than blindly replayed. A current row count of zero does not prove a delayed prior append cannot arrive. Duplicate/corrected evidence uses the existing append-only correction mechanism.

A broker transition and a native append cannot share a database transaction. Likewise, a SQLite/D1 reservation and a GitHub mutation are not a distributed atomic transaction. Retain the distinction between `LeaseGrant`, `WriteReservation`, `NativeWriteOutcome` and `DeliveryReceipt`; only the last two can report the externally observed effect. No first-phase synthetic receipt is labeled a real Work Events/Git enforcement receipt.
