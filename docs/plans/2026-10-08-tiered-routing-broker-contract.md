## Admission and request ABI v1

The v1 broker accepts one strict UTF-8 JSON request, at most 32 KiB, with exactly the fields below. Reject duplicate keys at any depth, nonfinite numbers/overflow, invalid Unicode/surrogates, multiple documents, unknown fields, depth above 16 containers, coercion and Boolean-as-integer values. Canonical request bytes use sorted keys, compact separators, ASCII escapes and one final LF. The broker records their SHA256 independently of input_sha256.

| Field | Exact type and meaning |
|---|---|
| task_id | Lowercase 32-hex opaque idempotency key; no source title or path |
| input_sha256 | Lowercase 64-hex hash of the complete rendered provider-neutral payload, including system/guidance/messages/citations; the transport must recompute it |
| disclosure_scope | Exactly public, synthetic, or local_private; a trusted policy admission for that exact input hash must agree |
| operation | Exactly navigation, coding_review, or mathematical_audit; determines Tier 1, 2 or 3 respectively |
| required_capabilities | Sorted, unique list of 1–16 reviewed capability IDs, each ASCII `[a-z][a-z0-9_]{0,63}`; every capability needs exact deployment evidence |
| account_id, provider_id, deployment_id, model_id | Four ASCII identities matching `[A-Za-z0-9][A-Za-z0-9_.:/-]{0,127}`; exact match with the policy-selected deployment, without wildcard, control characters, case normalization or alias substitution |
| policy_sha256, price_sha256 | Two lowercase 64-hex identities for the trusted admitted policy/price records |
| budget_id | Opaque lowercase 32-hex identifier for one authoritative USD ledger account |
| max_cost_nano_usd | Exact integer 0..2^63-1, a request ceiling rather than permission to spend beyond the account limit |
| deadline_unix_ms | Exact integer 1..2^63-1, checked against trusted host time at reservation and immediately before dispatch |
| context_tokens | Exact integer 1..1048576; actual tokenized input plus the bounded output reserve must fit this value and the deployment limit |
| max_output_tokens | Exact integer 1..131072, no greater than context_tokens or the deployment's tested hard cap |

No request endpoint, URL, credential, arbitrary provider parameter, retry, fallback, classifier, compression, tool destination or optional trust override is accepted. A trusted deterministic policy selects an exact deployment for the operation/capabilities/disclosure/bounds; requested identities must equal that selection. If its tier has no admitted capable deployment, return DENIED without selecting another tier. V1 has no automatic escalation; a later explicit governed escalation creates a new task, linked in the external task record with reason and charges, rather than mutating the original task.

The trusted policy is bounded data, separately pinned and reviewed. It binds exact input-hash/disclosure admissions, route priority, allowed operations/capabilities, limits, account/deployment status, validity period, storage authority and price-card identity. Caller claims of public data, model support or account identity supply no authority. An API admission record needs a root-associated original real-call result and capacity evidence for that exact account/deployment/model/API/SDK; documents and declared flags alone are insufficient. Synthetic TEST admission records are permitted only by the first test-only surface and can never authorize a real transport.

The broker obtains input count N only from the trusted `input_token_admissions[input_sha256][deployment_id][tokenizer_sha256]` record described in Unit 1. The request supplies a payload hash and bounds, never an authoritative count or count-evidence field. Missing exact keys, mismatched deployment/tokenizer, unavailable count evidence or a changed trusted record denies before reservation or dispatch. Retain the selected record's canonical SHA256 with the task. Require N + max_output_tokens <= both request context_tokens and deployment max_context_tokens, and enforce the deployment max_output_tokens separately. No subtraction of output capacity from context_tokens manufactures an observed input count.

## Integer price and account contract

USD uses nano-USD, scale 9, with exact integers and explicit price-card validity. Rates are integer nano-USD per one million billable tokens; component calculations use integer ceiling division, never floats. Input, cached input, cache writes, output/reasoning and any fixed charge must have a known conservative bound. The first runtime profile disables server tools, batch, external retrieval and paid classifiers. Unknown or unbounded billable components deny before dispatch; a missing rate is never zero. Explicit local provider charges may be zero, while local resource cost is separately measured or UNKNOWN.

For admitted input count N, input/cached-input/cache-write rates I/C/W, output rate O, output ceiling M=max_output_tokens, and fixed charge F, the exact reservation is ceil(N * max(I,C,W) / 1000000) + ceil(M * O / 1000000) + F. Ceiling is integer division `(numerator + 999999) // 1000000`; zero numerators yield zero. All three input rates must be known even if a fixture expects no cache use. This maximum covers a cache-write rate above the ordinary input rate and does not assume a cache hit. The adapter must prove its API parameter constrains every billable output component; otherwise admission is unavailable. Reject reservation arithmetic outside 0..2^63-1. A caller's ceiling must cover the upper bound, and account spent + outstanding held + this reservation must not exceed the configured account limit.

Known usage has inclusive input n, cached subset c, cache-write subset w and inclusive output o. Require c+w<=n and reasoning_tokens<=o; ordinary input is n-c-w. The exact known charge is ceil(((n-c-w)*I + c*C + w*W)/1000000) + ceil(o*O/1000000) + F. Round the combined input subtotal once: rounding three subsets separately can exceed the specified maximum reservation even when all rates agree. Reasoning is already included in o and is never charged twice. Provider accounting that does not fit this exclusive input partition/aggregate-input-rounding/inclusive-output profile cannot be admitted as KNOWN. Use the task's pinned price card, including for later settlement after its validity window; a newer card cannot reprice an earlier attempt. Fresh price validity and identity are required at dispatch. Preserve a provider-reported contradictory charge and freeze the account instead of replacing it with this calculation or discounting the reservation prematurely.

Each account binds currency/scale, limit, held amount, recorded spend, policy/price identity, status and version. Its scope is explicitly BROKER_TRAFFIC; these limits do not claim control of unrelated charges on a shared upstream billing account. Any broader account-wide ceiling needs separately verified spend/exclusivity and denies when that authority is unknown. SQLite is the sole authority in Unit 1. Redis is explicitly NOT_USED, not silently treated as available. Any later configured database/Redis/account authority that is unknown, unavailable, stale or unverifiable denies before an attempt. No memory-only budget, reset-on-restart balance, automatic quota refill or force-unlock is permitted.

## Durable state, replay and settlement

| State | Durable condition and allowed next action |
|---|---|
| reserved | One atomic account debit-to-held and task record exist; no provider attempt has occurred. Dispatch requires fresh admission checks and an atomic claim. Expiry/revocation before dispatch can confirm nondispatch and release. |
| dispatching | The sole attempt ID and claim are committed before any transport invocation. Only the claim winner may invoke that transport once. Replay or process recovery cannot invoke it again. |
| completed | A bounded observed result/error and immutable completion fingerprint are durably retained. Actual billing is KNOWN or explicitly UNKNOWN with the upper bound still held; only trusted complete/settle accounting can change the financial state. |
| confirmed_not_dispatched | Trusted controller evidence establishes zero transport attempts; release the reservation atomically. An HTTP rejection after an attempt is not this state. |
| unknown_delivery | An attempt may have happened but completion cannot be established. Retain the reservation, attempt identity and uncertainty; no automatic retry, fallback, expiry release or lower-tier dispatch. |

The uniqueness domain is task_id within the single governed ledger. Same key/input hash AND identical canonical control request returns the retained receipt/state/result reference without a new reservation or attempt. Different input hash refuses. Same input hash with changed account/route/scope/policy/budget/bounds also refuses, preventing replay from becoming a reroute or disclosure bypass. The persisted original native execution context is preserved on replay; it is not relabeled as the later reader's run.

Commit dispatching before releasing the SQL transaction and invoking the transport; never keep a database write transaction open during inference. The same claim transaction enforces the deployment's admitted max_parallel_attempts; active dispatching/unknown tasks hold a capacity slot conservatively until reconciled. Unknown capacity denies rather than queuing an unbounded call. Crashes before the dispatch claim leave zero attempts; crashes after the claim, including before a socket write, conservatively recover as unknown_delivery. Durable committed dispatching also covers successful provider delivery followed by a lost database completion write. Provider idempotency may later reduce uncertainty only after compatibility evidence; this design makes no provider-level exactly-once promise.

Completion and settlement have separate durable identities. `complete` fingerprints the exact canonical `{attempt_id,outcome,usage}` bytes using the same sorted ASCII JSON plus LF. The first trusted completion may change dispatching or unknown_delivery to completed when the controller establishes the bounded observed result/error. Identical complete replay returns its retained receipt bytes without an event, spend increment or hold release; any changed outcome, result, provider request identity or usage refuses and preserves the first completion. In particular, complete replay with formerly null usage changed to KNOWN is a conflict: later billing uses settle. An independently retained native terminal observation is needed to resolve unknown delivery; a billing record alone is insufficient.

`settle(attempt_id, settlement_id, usage, accounting_evidence)` is a separate trusted controller operation with the closed ABI below. It records nonnegative exact-integer usage/charge and original accounting-source identity, not caller assertions or model text. Missing usage remains UNKNOWN, never default zero. A single governed ledger gives settlement_id global uniqueness; the canonical complete settlement packet supplies its SHA256. Identical settlement-ID/packet replay returns the original receipt without an event or financial mutation, including after process restart. Reusing that ID with any changed bytes refuses. Each attempt also has at most one accepted KNOWN accounting fingerprint: a different settlement ID cannot apply the charge again. A successful confirmation of identical accounting under a new ID commits only that ID's immutable packet fingerprint/original receipt, without another accounting event, spend increment or hold release; this prevents later reuse of the ID for different bytes or another attempt. Conflicting accounting refuses while preserving the first fact and holding further account admission for reconciliation.

The economic fingerprint hashes canonical `{attempt_id,usage}` bytes and is bound to that attempt's immutable account/route/input/request/policy/price/tokenizer records. It is shared by known usage first received through complete and later settle confirmations. Completion/evidence/settlement fingerprints remain separate: a completion identity newly available after unknown delivery does not manufacture a different charge or permit another spend application. Accounting evidence must describe the complete final total for that one attempt and every admitted billable component; a partial usage sample or interim invoice cannot release the hold as KNOWN billing.

For completed/UNKNOWN billing, one BEGIN IMMEDIATE transaction persists settlement/evidence, changes billing to KNOWN, adds actual charge to spent once, releases exactly that task's still-held reservation once and records the resulting receipt/event. Result bytes/hash, completion fingerprint, attempt/route/native context and independent acceptance remain unchanged. Completed/KNOWN accounting from an earlier complete is already applied; settle can confirm identical accounting without charging again, and conflicting accounting cannot overwrite it. A failed or ambiguous commit retains the original durable state until status is read; no success, refund or retry is inferred.

For unknown_delivery, trusted settlement may record KNOWN billing and add observed charge once, but leaves delivery unknown, the entire reservation held and the capacity slot occupied. This deliberately conservative spent-plus-held amount cannot be reused as budget. A later independently established terminal complete may release that held reservation once; previously applied spend is not added again. Its usage must be null or match the retained KNOWN accounting exactly. Billing evidence cannot establish terminal delivery, send again or authorize fallback. Settling reserved, confirmed_not_dispatched or an unknown attempt refuses. Contradictory/over-bound actual charge is preserved as observed spend, freezes the account and marks the invariant violated; it is never truncated to the reservation, refunded or rolled back to make the ledger look safe. If an aggregate exceeds the signed ledger range, retain exact charge facts and an exact decimal aggregate in the append-only accounting event, freeze the account and return spent:null/invariant_status:VIOLATED rather than an overflowing or saturated balance. A completed result is not an independently accepted task.

## SQLite and filesystem boundary

Completion, settlement and nondispatch are trusted controller interfaces, not statements accepted from model text or a public request. No database is created by this document.

Use fixed parameterized statements, exact schema/version checks, no ATTACH/DETACH, no extensions, no caller SQL/PRAGMA and no unreviewed triggers/views. The fixed TEST observation views in the appendix are the only admitted views in Unit 1; their actual definitions still need implementation source review. Require a compatible actual sqlite3 runtime and collect its identities. Serialized writes use BEGIN IMMEDIATE, a bounded 1000 ms busy wait, commit/rollback propagation and conditional single-attempt state updates. Use journal_mode DELETE and synchronous EXTRA, verified on every connection, plus foreign_keys ON, trusted_schema OFF and read_uncommitted OFF. SQLite documents that an immediate transaction can return SQLITE_BUSY and that EXTRA adds the directory sync for DELETE-mode commit; this chooses conservative commit behavior without claiming a tested power-loss guarantee. [Transactions](https://www.sqlite.org/lang_transaction.html), [Synchronous modes](https://www.sqlite.org/pragma.html#pragma_synchronous).

Production storage must be a separately governed, private single-host filesystem, unavailable to product/model sandboxes and arbitrary same-UID writers. Refuse linked/special/foreign-owned roots, database or sidecars, unknown schema, corruption, full storage, busy/failed transactions and unknown reserve before any attempt. No-follow prechecks do not alone prove race freedom for SQLite's filename-based opens: Unit 1 uses an exclusively owned fixture namespace; hostile namespace replacement remains outside an admitted production claim until the storage/controller owner verifies that isolation. DB/journal identity and durability under process restart are tested; power-loss, network/shared-filesystem, backup restore, multi-host and malicious same-UID guarantees remain NOT_RUN. Restoring a stale ledger cannot release uncertain reservations or authorize new calls without reconciliation.
