## Synthetic SQLite experiment

All values are public TEST identifiers. Every connection, including the file-backed runtime-feature probe, child writers, lock holder, initial creator and reopened reader, sets and verifies busy_timeout 1000, journal_mode DELETE, synchronous EXTRA (value 3), foreign_keys ON (value 1), trusted_schema OFF (value 0) and read_uncommitted OFF (value 0). Connections use explicit transaction control. The program uses fixed SQL and bound parameters, a single tiny known schema and stdlib multiprocessing with the spawn context. It loads no extension, accepts no caller SQL and imports no routing broker.

Each caller mode runs eight fresh databases. Each round starts sixteen independent processes, verifies their connection settings and readiness, and releases them together. Each process attempts exactly one BEGIN IMMEDIATE with the unchanged1000ms busy timeout and no retry. An admitted transaction performs one conditional update and one commit; exactly one must change one row. Every other process either commits a zero-row CAS or records an explicit SQLITE_BUSY refusal at that BEGIN, with no entered transaction, no conditional update or commit, null changed-row count, actual elapsed time and fixed PID/token/settings/counts. These two nonwinner outcomes remain separate in all original results and the receipt. An error at update/commit/another stage remains failure; an unclassified error cannot be relabeled a safe BEGIN refusal. Every contender exits and closes its connection. A new connection verifies the exact schema, integrity_check, one committed winner and disappearance of the DELETE journal. The workflow never retries a refused operation or reruns its database for a cleaner result. This changed experiment measures single-winner safety with lawful bounded refusal; it does not establish that all sixteen operations acquire the write transaction before the busy deadline.

A separate fresh database makes busy refusal deterministic. The child opens and verifies its connection first; the parent then acquires BEGIN IMMEDIATE and holds the write lock while the child attempts BEGIN IMMEDIATE exactly once. The child's configured busy_timeout is 1000ms. It must return SQLITE_BUSY without entering a transaction or changing the row. The result records the actual observed elapsed time, with an explicit 0.8–2.0-second scheduling allowance for the hosted process; this allowance does not change the configured SQLite 1000ms wait. The parent rolls back its own harmless fixture transaction after receiving the refusal, closes and reopens to verify the unchanged row. There is no retry, forced database unlock, task redispatch or budget mutation.

Each successful normal or optimized caller therefore produces eight retained 16-contender CAS results and one retained busy-refusal result. Distinct actual child PIDs are checked alongside the fixed TEST token inventory. Completed and partial child observations are retained when a round fails. The normal and optimized executions must agree on actual runtime identities and restriction observations. Their nondeterministic winning TEST tokens, actual PIDs and measured busy latencies are retained as original observations; byte-identical race winners are not required.
