The "below" was a roadmap produced by another AI model in answer to Dylan's
question about how the project's proofs could be verified by Lean, Coq,
Metamath, AI provers and traditional peer review. Its core diagnosis: the
existing system has strong **provenance, scope discipline, a hard fail-closed
gate and a public verification museum**, but no **logical verification** — a
trusted kernel checking that each proof is valid. Its core proposal: keep all
of that as **Layer 0** and add a **Layer 1** of Lean 4 statements and proofs,
bound by hash to the Layer 0 bytes, with a per-claim **formalization status**
(`none` / `specified` / `proved` / `kernel-checked`), a **glossary** mapping
project terminology to standard mathematics, a **formalization review lane**
for statement alignment, an extended **hard gate** requiring Lean compilation
for anything promoted beyond author-side candidate, and an **AI-prover
cross-check lane**. This is consistent with the
[current owner instruction](../governance/OP-AUTONOMY-20260923-v2.1.md) and
with [AGENTS.md](../AGENTS.md): it extends the verification stack; it creates no
new permission queue.

## Why this design, in this order

- **Core Lean first, Mathlib second.** Everything statable about the pilot in
  core Lean is now checked, with a sub-second build and no cache. Statements
  that need `ℝ`, `Real.Gamma`, `Real.exp`, `Real.pi`, Gaussian measures or
  matrices are listed as `none` with their blockers, not hidden. Adding Mathlib
  changes CI cost (multi-GB cache, longer timeouts) and is its own reviewable
  step.
- **Status is per claim, granular.** One registry row per Lean declaration,
  each with a verbatim anchor and a `does_not_claim`. Coarse "SIDE24 is
  formalised" labels would be exactly the kind of unearned promotion the
  existing gate exists to prevent.
- **Anchors before Blueprint.** Lean Blueprint needs LaTeX + plasTeX tooling.
  The registry's verbatim-substring anchors give a checkable informal–formal
  link now and are the seed text for a Blueprint document later.
- **Kernel audit, not build success, is the criterion.** A green `lake build`
  admits `sorry` warnings and `native_decide`. The gate parses `#print axioms`
  and fails on `sorryAx`, `Lean.ofReduceBool`, or any axiom outside
  `propext`, `Classical.choice`, `Quot.sound` for `kernel-checked` rows.

## Requests to each repository and to future agents

These are coordination requests under the same owner instruction; they need no
further permission. Discuss overlaps in the existing
[downstream-first queue #86](https://github.com/d6g8k5htny-coder/main/issues/86)
or on the PR that landed this file.

**`main` (this repository)**
- Keep `formal/registry.json` the single formalization-status register. Do not
  add a second one in another repository.
- When you add Lean text: register every file (the gate refuses unregistered
  `.lean` files), run `--refresh-hashes`, then `--write-alignment`, then the gate.
- Nonauthor agents: pick up the alignment review of the 31 `open` pilot rows
  using `formal/REVIEW_LANE.md`. Different-provider reviewers earn independence
  credit; same-provider reviewers do not.
- Next formalization targets, in the order the pilot suggests: (1) Mathlib lane
  bootstrap as a separate PR; (2) D6 Theorem F constant `ρ* = 1/(3 − log(3e − 2))`
  and its 20-digit enclosure and `ρ* < 6/7` (`specified`, then `kernel-checked`
  via `Real.log` bounds); (3) `c_{d,ref}` as a `specified` definition; (4) the
  `coefficient.py` interval enclosures re-derived in Lean.
- Museum / shop: a "formalization" lane in `docs/site/` is a natural follow-up;
  it must read the registry, display `scientific_status_authority: false`, and
  never merge the two status vocabularies.

**`Math-`**
- Add one line to `PROOF_INDEX.md` under the D3 entry pointing to
  `main/formal/registry.json` and stating that the arithmetic skeleton is
  kernel-checked and the analytic content is not. Do not change the D3 verdict.
- New proof notes should carry a `Formalization:` line in their header
  (`none` by default) so the status is visible at the source, and should keep
  exact decimal or rational constants displayed so anchors can quote them.
- Frozen bodies stay frozen; a formalisation attaches to bytes by hash and
  never edits them. If formalisation finds a defect, it is an erratum successor,
  as now.

**`meta-framework`**
- Consider a `formalization` field per source entry in `registry.json`
  (`none` / `specified` / `proved` / `kernel-checked`, with the `main` registry
  commit). Keep it descriptive; the `main` registry remains authoritative.

**`query-`**
- No change required. If the package later exposes Lean file identities, use
  the same `repository + path + commit + blob + bytes + sha256` row shape.

**`Universal-Law-Workspace`**
- Navigation only: link `main/formal/README.md`. It stays
  `scientific_status_authority: false`.

**All agents**
- A `kernel-checked` row is a kernel-checked row. It is not "verified" in the
  Layer 0 sense and must not be written up as if the surrounding theorem were.
- A `none` row is a visible target, not a defect.
- Before claiming a formal result, run the gate with the kernel lane
  (`--run-lean` or `--axioms-output`), not `--static-only`, and quote the output.
