# Frozen-object custody supplements

## Why this directory exists

`tools/frozen_check.py` compares the `frozen_objects` register tab against
`drive/inventory.jsonl`. That comparison is worth something only because the two
are *independent* Drive-side records of the same bytes: the register says what a
frozen object's digest should be, the accessibility publication says what Drive
measured, and they either agree or they do not.

`drive/inventory.jsonl` derives from one dated publication — 4,456 of the 4,456
rows of `drive/source_map/Files.csv`, as of 2026-09-17. Objects frozen **after**
that date cannot be in it, and no faithful inventory will contain them until the
publication is re-run. Eleven `frozen_objects` rows are in exactly that
position. Without a supplement, `frozen_check` refuses all eleven, and the
register export that carries them cannot be adopted.

A supplement fills that gap, and it is a place where a **non-independent** record
could get in — deliberately, or by someone copying the register's own expected
digest because it was to hand. Nothing mechanical can tell a genuinely
downloaded digest from a copied one. So the checker does not pretend to: a row
answered from a supplement is reported `MATCH_VIA_CUSTODY_SUPPLEMENT` and
counted apart from `MATCH`, permanently, and a supplement may never answer for a
Drive ID the publication already covers.

## If you are about to add a custody row, read this

**A row that exists is a row the checker will answer from.** An object you have
not yet downloaded and hashed does not belong in `rows` at all — not with a
placeholder, not with the register's value pending confirmation. List its Drive
ID under `_pending` instead. That is the whole reason `_pending` is a separate
key rather than a comment.

**Say who collected it.** Every row carries `verified_by`. `frozen_check` counts
the rows that two or more *distinct* collectors reported identically and prints
that count separately; two files naming the same collector are one collector
twice and are counted once. Mislabelling a collector is how that count stops
meaning anything.

**Do not import by hand.** A publication from another agent is retained byte for
byte under `imported/`, its length and SHA-256 pinned in
`tools/custody_import.py`, and the supplement `frozen_check` reads is
*generated* from it. `python3 tools/custody_import.py --check` fails CI on
drift, exactly as `tools/registers_import.py --check` does for the register
exports. Repair happens at the source, never in the generated file.

**Conflicts are refused, not resolved.** If two supplements give the same Drive
ID different bytes or a different digest, the ID is dropped and the conflict is
reported. There is no file ordering that makes choosing between two
contradictory records safe.

repaired the same run reports `problems=0`.

## What none of this establishes

Downloading an object and hashing it establishes that those bytes carried that
digest when they were fetched. Retaining another party's publication establishes
what that publication said. Neither establishes that an object is what the
register says it is about, that its contents are correct, or that anything it
claims mathematically holds. No row here re-freezes anything, verifies a body,
moves a gate, discharges a premise or closes an obligation.

Agreement between two collectors is evidence about bytes and nothing more. In
particular it is **not** organizational-independence credit, which is a question
about who reviewed an argument, not about who downloaded a file.
