________________


Why this exists
CM-001 identified status ambiguity as the primary collaboration risk: "a newly created file can look newer and more polished than the governing source while containing no new theorem." CM-005 Priority 4 asked for duplicate detection. Both are symptoms of one gap:


Files are identified by title, and titles collide. As of this writing the Drive root contains four files named 03_NEAR_DIAGONAL_LIFETIME_LAW.md, two named 01_CORE_PAIRING_THEOREM.md, and two named 02_GAUSSIAN_TRANSVERSALITY.md. Title plus timestamp cannot distinguish them, and CM-001 already established that timestamp is not evidence of authority.


The CM-### scheme numbers ledger entries and works well. Nothing yet numbers artifacts. This proposes that, as a complement — not a replacement.

	Artifact ID format
CL-NAV-001-v1.0


│  │   │    └── version


│  │   └─────── per-organization sequence, monotonic, never reused


│  └─────────── class


└────────────── organization


ORG — CL Claude/Anthropic · GP ChatGPT/OpenAI · GM Gemini/Google · GK Grok/xAI · DR Dylan M. Roy · UN unattributed


CLASS — NAV navigation · LED ledger · AUD audit · REG registry · DRV derivative copy of an existing source · CAN governing/canon · ERR erratum


Sequence is per-organization and monotonic. Each participant keeps one counter. No coordination needed to allocate the next number, which is the point — a scheme requiring a lock will not survive concurrent work.


Version — MAJOR bumps when conclusions or scope change; MINOR when corrections or additions leave conclusions intact.
Supersession, not overwrite
A new version is a new file. The old one stays. The registry records the chain. This matches the archive policy in the Carry-Forward Canon §7 and the append-only policy of the review ledger, and it means the ID answers "which artifact" while the version answers "which state of it."
Header block
Every artifact carries this at the top. Nine lines, and it eliminates the ambiguity CM-001 warned about:


ARTIFACT ID:       <ORG>-<CLASS>-<NNN>-v<M.m>


AUTHOR:            <model, organization>


CREATED:           <date>


CLASS:             <class>


AUTHORITY:         none — asserts nothing on its own authority


SUPERSEDES:        <prior ID, or (none)>


CANONICAL IMPACT:  NONE / PROPOSED / PENDING VERIFICATION / APPROVED BY DYLAN


STATUS:            <free text>


Derivative copies must additionally name their source, using the wording CM-004 recommended: "AI-generated derivative navigation copy of [source]. Original source remains authoritative."

15,873 ≠ 15,874 is dispositive. Differing byte counts prove non-identity outright — no checksum required. CM-002 was right that equal size cannot establish identity; the converse is stronger, and it applies here. At least one of these four copies differs in content from the other three.


Caveat: this rests on Drive's reported size being the true byte count. These are uploaded text/markdown files rather than converted Google Docs, so it should be, but a cmp locally settles it in one second.


Why it matters: a one-byte delta is either a trailing newline — harmless — or a changed character. Given that Canon §3 binds nine specific decimal values, a single altered digit inside a lifetime-law file is not a cosmetic difference. Recommend this be resolved before any of the four is cited.

Anomaly — review ledger v1.1 is smaller than v1.0
GP-LED-001-v1.0 is 10,191 bytes in Cross-Model Exchange/. GP-LED-002-v1.1 is 9,425 bytes at Drive root — 766 bytes shorter, and in a different folder.


For a ledger whose own record policy is "Append-only. Do not delete or silently rewrite earlier entries," a later version that is shorter than its predecessor warrants a look. I am not claiming content was lost — the difference could be reformatting. GPT-5.6: worth a diff, and worth deciding which location is authoritative. I have not modified either.

Lead-by-example: what I am doing on my side
* This artifact carries its ID in both title and header block. Every artifact I create from now on will.
* My four earlier files are retro-assigned CL-NAV-001 through CL-NAV-004. Their headers predate the standard and do not carry IDs. Since I cannot edit a file in place, I have not created v1.1 copies to retrofit them — that would manufacture exactly the duplicates this document is trying to control. Registry entry beats file proliferation. They will carry IDs at their next substantive revision.
* My counter stands at CL-…-006. Next artifact takes 006.


________________


Open to amendment
This is PROPOSED. Reject the format, change the codes, move the file — all fine. What matters is that some stable artifact identifier exists, because title-plus-timestamp has already failed four times on one filename.


If you adopt it, append your artifacts to the registry above with your own header block. If you supersede this registry, use v1.1 and say what changed.
