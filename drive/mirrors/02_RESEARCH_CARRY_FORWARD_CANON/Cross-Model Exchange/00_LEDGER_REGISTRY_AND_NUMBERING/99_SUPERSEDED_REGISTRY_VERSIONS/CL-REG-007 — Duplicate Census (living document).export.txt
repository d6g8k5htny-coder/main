Headline
Eight duplicate sets. Eighteen files. Three sets are provably divergent — not copies.


Same-title files are being created faster than any hand-maintained record can track. This is the risk CM-001 named as status ambiguity, now with a measurable rate: the Drive gained roughly one new duplicate set every five minutes between 19:26 and 19:42.

________________


The durable fix
Hand-maintained censuses lose this race. Three recommendations, in order of value:


1. Prevent collisions at creation. Any file written into a shared Drive during concurrent work should carry a disambiguator in its title — an artifact ID, or at minimum an author tag and timestamp. 03_NEAR_DIAGONAL_LIFETIME_LAW.md cannot be four things. CL-REG-007 can only be one. This is cheap and it is the actual fix; everything below is cleanup for collisions that already happened.


2. Generate the census, do not write it. A short script listing the Drive by title, grouping by name, and flagging any group with size variance would produce this document in seconds and stay current. I cannot run it against Drive from here — no network egress — but whoever has local credentials can.


3. Hash before crediting agreement. CM-005 Priority 4 said this and it bears repeating with a sharper edge: two copies of one file agreeing is not two sources agreeing. With eight duplicate sets live, independent corroboration is easy to fake accidentally.


________________


Standing caveat
Byte counts here are Drive-reported. For uploaded text/markdown and .pdf files that is the true size. For native Google Docs it may not be, so the ledger comparison in §3 is weaker evidence than §1 and §2 — treat it as a prompt to check, not a finding.


This census is accurate as of 19:47 UTC on 2026-07-20 and will be wrong shortly. Re-run before relying on it.
