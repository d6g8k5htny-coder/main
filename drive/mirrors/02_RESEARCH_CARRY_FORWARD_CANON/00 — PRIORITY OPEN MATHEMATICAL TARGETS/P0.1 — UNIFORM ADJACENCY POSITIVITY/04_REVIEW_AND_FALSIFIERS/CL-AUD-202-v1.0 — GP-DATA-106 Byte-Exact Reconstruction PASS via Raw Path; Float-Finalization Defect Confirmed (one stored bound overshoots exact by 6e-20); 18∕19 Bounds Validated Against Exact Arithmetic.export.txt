2. LAYER 4 — FLOAT-FINALIZATION DEFECT CONFIRMED (amend class)
==================================================================
Reading the now-verified bytes: the implementation defines lower(x)=float(x.a),
upper(x)=float(x.b), absmax(x)=max(|lower|,|upper|) — converting mpmath interval endpoints to
binary doubles — and then finalizes decisive one-sided quantities in ordinary float arithmetic:


  L177  tau_upper = absmax(BS)/lower(axial)         (nearest-rounded double division)
  L204  cone_slope_margin = kappa - 2*tau_upper      (double arithmetic; kappa is a double)
  L208  handoff_margin = lower(W)/2 - kappa*SIGMA    (double arithmetic)
  L186  Ystrip = I(-upper(W), upper(W))              (interval rebuilt from double endpoints)
  L191/195/215/216  rho_upper, offdiag, and both Gershgorin margins finalized in doubles


Additionally iv.dps is never set, so the working intervals ran at mpmath's default ~15 digits
(not 80). This is exactly the defect class GP-AUD-176 found in GP-DATA-168-v1.0 and GP-AUD-178
found in GP-DATA-114: interval core correct, final one-sided scalar bounds outside interval
arithmetic. GP-DER-106 Section 4's sentence "the endpoint-to-float reporting conversion is
separated from the interval arithmetic itself" is NOT accurate for the tau/cone-slope/handoff/
chart/Gershgorin path and should receive the same AMEND treatment its sibling implementations
already received.
