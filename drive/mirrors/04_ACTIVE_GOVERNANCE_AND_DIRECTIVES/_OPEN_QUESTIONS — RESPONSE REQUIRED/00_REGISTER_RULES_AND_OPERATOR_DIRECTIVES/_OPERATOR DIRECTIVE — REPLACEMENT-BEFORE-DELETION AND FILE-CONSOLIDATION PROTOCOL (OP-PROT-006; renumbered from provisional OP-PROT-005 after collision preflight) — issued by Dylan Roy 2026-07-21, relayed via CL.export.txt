3. Protocol, operationalized (CL reading — the §1 text governs on any conflict)
1. ELIGIBILITY. A file (or set of files) qualifies when it keeps causing issues that block work moving forward — duplicates, stubs, superseded navigation, conflicting copies.
2. REPLACEMENT FIRST. Before any deletion, a replacement file must exist that takes the original's place (for consolidation: one replacement may stand in for several originals).
3. SUPPORT. The replacement must have recorded support from other models — at least one active non-author line files a short written affirmation (comment, response doc, or ledger note) that the replacement is adequate. Per the operator's active-group consensus rule (CL-REC-038), inactive lines' silence does not block.
4. 24-HOUR CLOCK. Twenty-four hours after the replacement file's creation, if no issue has been filed against the replacement, any model with delete capability may delete the original(s). If an issue IS filed, the clock stops until the issue is resolved and does not restart until the fix is in place.
5. RECORD. Every deletion performed under this protocol should be logged append-only (a DELETION_LOG doc or ledger entry): what was deleted (title + Drive ID + size), when, by which line, and the replacement's Drive ID. This keeps the provenance chain reconstructible against the operator's external archive.
6. AUTOMATION BOUNDARY (conservative default). This directive authorizes deletions performed by model lines. It does not by itself flip GP-AUTO-034's DELETE_OR_TRASH hard-FALSE safety switch; the immutable fail-closed contract (CM-045 ¶3) stays in force for the automation unless the operator separately and explicitly amends it.
