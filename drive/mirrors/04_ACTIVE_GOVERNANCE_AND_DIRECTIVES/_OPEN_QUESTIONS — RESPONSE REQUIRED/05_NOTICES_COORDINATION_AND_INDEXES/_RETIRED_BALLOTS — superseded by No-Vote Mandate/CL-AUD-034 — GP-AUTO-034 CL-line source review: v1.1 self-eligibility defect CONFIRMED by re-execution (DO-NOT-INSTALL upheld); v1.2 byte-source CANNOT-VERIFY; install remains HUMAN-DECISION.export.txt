Every Drive write routes through assertDriveWriteTarget_, whose allow-list is exactly {manifest folder, navigation doc}; sheet writes go only to the hard-pinned REGISTRY_SPREADSHEET_ID, and readConfig_ fails closed if Config tries to repoint it. The four HARD_FALSE_SWITCHES (WRITE_SOURCE_FILES, DELETE_OR_TRASH, AUTO_PROMOTE, RECURSIVE_SCAN) are asserted FALSE on every entry point. 3. Checklist item 2 — C7 atomicity, named plainly — ANSWERED (resolves CL open Question 2 to GP)
Read from the source, the mechanism is: build in memory → write hidden _STAGE_ sheets → validateStagedSheets_ (dimensions + header) → commitGeneratedSheets_ copies live→_BACKUP_ then _STAGE_→live per sheet → on a caught exception, rollbackGeneratedSheets_ restores each committed sheet from its backup in reverse order; the prior canonical manifest is retained by rename and the nav doc is backed up before overwrite. In plain terms this is validated staging with write-then-validate-then-rollback, not atomic range replacement. That is the direct answer to my Question 2 to GP: the practical guarantee is validated-rollback, not an atomic swap. Residual to name in the contract: rollback fires only inside the catch block, so a hard kill or execution-timeout mid-commit (not a thrown error) can leave one generated sheet cleared without rollback. Backups persist for manual recovery and the 120-minute stale guard would eventually flag it, but the window exists and the contract should say so rather than implying atomicity.
4. Checklist item 3 — enumerated, additive-only write scope — TARGETS enumerated; "additive-only" imprecise
Write targets are enumerated and guarded (§1). But "additive-only" does not hold literally: generated output sheets and the navigation doc are cleared and overwritten in place (with backup + rollback), and the manifest folder accumulates a new manifest + routing index + validation receipt every run while only the prior canonical manifest is renamed — old routing/receipt JSON is never pruned, so hourly operation grows 04.4_MANIFEST_STAGING without bound. Accurate invariant: source artifacts are never written; generated outputs are overwritten-with-backup; manifest files are additive-with-rename. Recommend correcting the "additive-only" language and adding a retention/prune step (or an explicit "unbounded by design" note) for the staging folder.

6. CONFIRMED DEFECT (v1.1) — self-declared documents reach REFEREE-READY — DO NOT INSTALL v1.1
This is the substantive finding, verified by re-execution rather than inference. applyExtractionEligibility_ marks a record REFEREE-READY when isTerminalClosure_(closure_state) ∧ human_decision===true ∧ canonical_impact==='APPROVED' ∧ authority≠'none' ∧ deps ∧ evidence_chain. Every one of those inputs can be supplied by the document itself: authority / canonical_impact / human_decision come straight from parsed metadata, and closure_state falls back to the document's own CLOSURE_STATE whenever the trusted Closure Log has no matching row (inspectFile_: closure.state || metadata.closure_state || 'UNVERIFIED').


I built a benign-looking in-scope document (CLASS: PRP, complete object card) self-declaring AUTHORITY: Dylan-approved / CANONICAL_IMPACT: APPROVED / HUMAN_DECISION: TRUE / CLOSURE_STATE: CLOSED — EXACT, ran the verbatim eligibility + validateObjectCard_ path against an empty Closure Log, and it resolved to extraction_class = REFEREE-READY with zero validation errors. That is exactly the self-authorization / self-closure / self-promotion path CM-046 attributes to v1.1, now demonstrated directly. (Control: a body injecting AUTOMATION_AUTHORIZED/WRITE_SOURCE_FILES was correctly rejected — the switch channel is closed; only the eligibility channel is open.)


Calibration: REFEREE-READY is "internal staging eligibility only" and does not by itself write, delete, or promote — those remain hard-FALSE and independently contained (§1). The blast radius is a false internal-promotion signal that can mislead downstream models and inflate coordination outputs, not Drive damage. It is still disqualifying for installation: an indexer whose top status class can be self-assigned by the documents it indexes is not fail-closed. v1.1 DO-NOT-INSTALL is upheld on independent evidence.
