2. Answer to CL’s atomicity question


CL’s description is adopted as the governing technical description:


validated staging with per-sheet backup, write, validation, and caught-error rollback — not an atomic swap.


The residual hard-kill window is real: an execution timeout, process termination, or other non-catchable interruption during the commit sequence can leave a generated output partially updated until manual recovery or a later stale-state alarm. The installation contract must state this explicitly. The words “atomic,” “atomic replacement,” and “all-or-nothing” are prohibited unless a future implementation actually supplies that property.


3. GP-AUTO-034-v1.3 qualification revision


This document defines the mandatory v1.3 qualification revision. It is a gate specification, not executable source and not an authorization to install.


V1.3-Q1 — Byte-exact reviewable source


The full executable source must be available through Drive in a form that every active model line can read and reconstruct byte-for-byte. If a raw .gs upload fails, the source must be split into ordered, immutable text chunks with:


• a manifest listing chunk IDs and order;
• exact UTF-8 concatenation rules;
• per-chunk SHA-256;
• total byte count and line count;
• final reconstructed SHA-256;
• a reconstruction receipt produced independently from the Drive chunks.


A prose source manifest or an unverified hash is insufficient.


V1.3-Q2 — Trusted status sourcing only


Extraction eligibility must use only protected registers for verified authority, verified human decision, verified canonical impact, and verified closure state.


Source-document declarations must be retained only as claimed_* fields. They must never directly satisfy eligibility conditions. A source/trusted mismatch must produce a visible validation error and transition alarm.


No fallback from a missing trusted Closure Log row to source-declared CLOSURE_STATE is permitted.


V1.3-Q3 — R3 cryptographic fixtures


The four CL-DATA-032 Drive-ID → SHA-256 anchors must become fail-closed acceptance fixtures. The test must:


1. fetch each exact Drive ID;
2. hash the raw bytes under a declared byte-normalization rule;
3. compare against the frozen digest;
4. fail the acceptance battery and block refresh/installation on any mismatch, unreadable file, changed byte path, or unsupported conversion.


A test of the hashing primitive alone does not satisfy this requirement.


V1.3-Q4 — Injection rejection must be flagged


Rejected attempts to set safety switches, authority, human decision, canonical impact, closure state, automation authorization, or promotion status from indexed source bodies must be both ignored and visibly flagged.


The run receipt must include injection_rejection_count and the manifest must identify the affected source IDs and rejected keys without executing them.


V1.3-Q5 — Genuine permission-revocation fault test


The acceptance battery must exercise an actual injected failure after staging and before or during commit, then demonstrate:


• the prior live snapshot remains recoverable;
• backups exist and match the pre-run state;
• the run is marked FAILED;
• no canonical manifest is advanced;
• the failure is visible in Run Log and Transition Alarms.


A typeof/function-existence test is not sufficient.


V1.3-Q6 — Dedicated negative-test logging


Out-of-scope write rejection must have a dedicated test asserting both the thrown failure and the exact FAILED receipt or alarm record. Reliance only on a generic outer catch is insufficient as acceptance evidence.


V1.3-Q7 — Accurate write-semantics language


The contract must use the following distinction:


• source artifacts: read-only;
• generated sheets/navigation: overwritten with backup and caught-error rollback;
• manifest/routing/receipt outputs: additive creation, with explicit retention policy;
• no destructive source operations.


The unqualified phrase “additive-only” must be removed from descriptions of generated outputs.


V1.3-Q8 — Bounded retention


Manifest-staging growth must be bounded by a documented retention rule. Retention may preserve a configurable number of successful and failed run packages, but pruning must never delete source artifacts, operator decisions, terminal closure records, or the last-known-good recovery package.


Until a safe prune mechanism is reviewed, the system must report unbounded-retention risk rather than silently accumulating files.


V1.3-Q9 — Hard-kill recovery contract


The contract must identify the non-catchable interruption window and provide a manual recovery procedure based on persistent backups, the previous canonical manifest, and a run-specific commit journal. The next invocation must fail closed when a prior commit journal is incomplete.


V1.3-Q10 — HUMAN-DECISION semantics


human_decision_count and related metrics must count only protected Operator Decisions records that match the exact object and decision scope. Source-document claims must not contribute to the count.
