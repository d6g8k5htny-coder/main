1. PURPOSE


This revision repairs the material circularity and determinism defects identified in AO48-AUD-029-v1.0 while retaining R0.1’s stored-byte root, direct-enumeration, collision-hold, and participation-safety architecture.


It resolves five questions:
1. the exact stored byte object hashed by ROOT_SHA256;
2. the prohibition on manifest self-reference;
3. deterministic JSON canonicalization;
4. the partition between pre-root root-bearing leaves and post-root root-referencing attachments;
5. current participation and governance routing.


All unaffected provisions of TRC-STANDARD-001-v1.2 remain in force except any voting, roster, observer, or nonparticipation language superseded by OP-PROT-011. This revision changes package identity, assembly order, and routing rules only. It changes no mathematical closure, theorem, machine state, release, or deletion authority.


2. BINDING ROOT-HASH OBJECT AND CANONICALIZATION


2.1 Stored-byte root.
ROOT_SHA256 SHALL be the SHA-256 digest of the exact raw bytes freshly retrieved from the single declared canonical manifest Drive ID after that exact file passes a write-then-read verification transaction.


The bytes uploaded to Drive MUST already be canonical. A parser or reserializer is a validation control only and MUST reproduce the stored manifest byte-for-byte. Any mismatch in byte count or byte value makes the manifest noncanonical and gives it zero root and sealing credit.


Post-retrieval normalization is prohibited as a root-defining step. No trimming, BOM removal, newline repair, whitespace normalization, key sorting, encoding conversion, or parse-and-reserialize output may replace the retrieved stored bytes.


2.2 No self-reference.
The canonical manifest MUST NOT contain ROOT_SHA256, any digest of its own bytes, or any field derived from its own serialized content, and MUST NOT list itself among the enumerated leaves. ROOT_SHA256 is recorded only in post-root attachments under Section 3.2. A manifest containing a self-digest or self-enumeration is noncanonical and receives zero root and sealing credit.


2.3 Deterministic JSON representation.
JSON canonicalization SHALL follow RFC 8785, JSON Canonicalization Scheme, with these capsule-specific addenda:
- the JCS output is followed by exactly one LF; a validator using stock JCS output MUST append that LF before equality comparison;
- manifest values are restricted to strings, integers exactly representable in IEEE-754 double, booleans, null, objects, and arrays; floating-point values are prohibited;
- every array ordering rule MUST be declared inside the manifest in an explicit field;
- encoding is UTF-8, without BOM, with LF newline convention throughout.


2.4 Verification receipt.
The validation receipt MUST record expected bytes, retrieved bytes, parser/reserializer bytes, MIME type, byte count, SHA-256, Drive ID, retrieval time, and exact equality result.


For Google-native objects, fileSize metadata is diagnostic only. A claim that a native Doc, Sheet, or Slide is empty or populated MUST be based on body/content retrieval or a qualifying export, not metadata size alone.


3. NON-CIRCULAR PACKAGE MEMBERSHIP


3.1 Pre-root leaf set — root-bearing.
The canonical manifest MUST directly enumerate every carrier that exists and has passed round-trip verification at manifest-generation time, including:
- the four primary human-readable capsule documents;
- every evidentiary source or frozen export required by the capsule specification;
- the exact frozen register-row carrier;
- native-object export identity records;
- any reconstruction or link-validation receipt already published and verified before manifest generation.


Each Section 3.1 record MUST include:
- artifact ID and title;
- Drive ID and permanent link;
- MIME type and declared export representation where applicable;
- byte count;
- SHA-256;
- evidence role;
- active, correction, superseded, failed, collision, provenance, or zero-credit status;
- dependency relation;
- retrieval or revision identity.


The manifest MUST NOT enumerate itself.


3.2 Post-root attachments — root-referencing and non-root-bearing.
Artifacts that cannot exist before the manifest and root are established — including checksums.sha256, root_hash_receipt.json, validation_summary.json, and independent-review receipts — MUST NOT be enumerated as Section 3.1 root-bearing leaves.


Each Section 3.2 attachment MUST instead record the accepted ROOT_SHA256 and canonical manifest Drive ID, binding itself to the package by reference to the root rather than by inclusion in it.


3.3 Declared membership and completeness.
The rooted manifest MUST declare in explicit fields:
- the exact membership of the Section 3.1 pre-root set; and
- the expected membership of the Section 3.2 post-root set.


Omission in either class must therefore be detectable. Capsule completeness requires that every declared Section 3.2 attachment exists, is readable, and cites the accepted root and canonical manifest Drive ID. The root certifies only the Section 3.1 set.


3.4 Consolidated carriers and provenance.
Consolidated index carriers may be listed as additional Section 3.1 leaves but may not replace direct enumeration of any required Section 3.1 member.


A superseded, collision, failed, corrupt, or provenance-only object MUST either be excluded from the active Section 3.1 set or listed with zero root-bearing evidence credit. Same-purpose alternate carriers may not be silently substituted.


4. ASSEMBLY ORDER


The required sequence is:
A. freeze exact capsule scope, primary documents, evidentiary sources, register row, corrections, exclusions, and dependencies;
B. publish and independently verify every Section 3.1 carrier;
C. generate canonical manifest bytes under Section 2, upload once, retrieve fresh, and prove exact byte equality;
D. compute ROOT_SHA256 only from the verified stored manifest bytes;
E. generate Section 3.2 attachments that cite the accepted root and canonical manifest Drive ID;
F. perform qualifying non-author package review of the exact root, Section 3.1 set, Section 3.2 set, scope, and approval record;
G. seal only after every Section 6 gate passes.


No post-root attachment may be represented as committed inside the root. No pre-root required carrier may be hidden behind a post-root receipt.
