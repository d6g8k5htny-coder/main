1. PURPOSE


This numbered revision removes three ambiguities exposed during TRC-EC020-v0.3 assembly:
1. the exact byte object hashed by ROOT_SHA256;
2. whether consolidated carriers may replace direct leaf enumeration;
3. whether superseded Grok-participation language can create active review or evidence credit.


All unaffected provisions of TRC-STANDARD-001-v1.2 remain in force. This revision changes package identity and routing rules only. It does not change any mathematical closure, theorem, machine state, ballot, release, or deletion authority.


2. BINDING ROOT-HASH OBJECT


ROOT_SHA256 SHALL be the SHA-256 digest of the exact raw bytes of the single declared canonical manifest file after that exact Drive ID passes a write-then-read verification transaction.


The bytes uploaded to Drive MUST already be canonical. A parser or reserializer may be used only as a validation control and MUST reproduce the stored manifest byte-for-byte. Any mismatch in byte count or any byte value makes the manifest noncanonical and gives it zero root and sealing credit.


Post-retrieval normalization is prohibited as a root-defining step. No trimming, BOM removal, newline repair, whitespace normalization, key sorting, encoding conversion, or parse-and-reserialize output may silently replace the retrieved stored bytes.


For a JSON canonical manifest, canonicalization occurs before upload and uses:
- UTF-8;
- no BOM;
- compact JSON serialization;
- recursively sorted object keys;
- deterministic array ordering declared by the capsule specification;
- LF newline convention;
- exactly one final LF.


The validation receipt MUST record the expected bytes, retrieved bytes, parser/reserializer bytes, MIME type, byte count, SHA-256, Drive ID, retrieval time, and exact equality result.


3. DIRECT ROOT-BEARING LEAF ENUMERATION


The canonical manifest MUST directly enumerate every root-bearing leaf carrier. Each active leaf record MUST include:
- artifact ID and title;
- Drive ID and permanent link;
- MIME type and declared export representation where applicable;
- byte count;
- SHA-256;
- evidence role;
- active, correction, superseded, failed, collision, or provenance status;
- dependency relation;
- retrieval or revision identity.


Consolidated index carriers may be listed as additional leaves, but they may not replace direct enumeration of:
- the four primary human-readable capsule documents;
- every evidentiary source or frozen export required by the capsule specification;
- the exact frozen register-row carrier;
- native-object export identity records;
- checksum, reconstruction, link-validation, and independent-review receipts.


A superseded, collision, failed, corrupt, or provenance-only object MUST either be excluded from the active root-bearing set or explicitly listed with zero root-bearing evidence credit. Same-purpose alternate carriers may not be silently substituted.


4. ONE VERSION, ONE MANIFEST, ONE ROOT


A capsule version may have only one declared canonical manifest Drive ID and one active root candidate. A competing same-version bundle forces the version into collision hold. The repair is a numbered successor capsule version; no model may select a same-line candidate merely by preference or chronology.


For TRC-EC020-v0.3:
- Candidate A is preserved as a stored-byte-root attempt but has unresolved direct-enumeration completeness;
- Candidate B is preserved as a direct-enumeration attempt but hashes bytes different from its stored manifest;
- neither candidate is accepted;
- the conservative successor is TRC-EC020-v0.4, assembled under this revision after adoption.
