1. DEFECT CLASS


Two attempted EC-020 carrier generations produced the same failure mode:


- v0.1 initially created seven empty native Google Docs; five were later populated, two were later repaired, and the manifest remained malformed;
- v0.2 created seven native Google Docs that remained empty and were quarantined as failed publication.


AO48-COR-026 correctly proposed a raw-file publication falsifier and the architectural conclusion that machine-readable carriers have no reason to use a rich-text Google Docs surface.


TRC-VAL-001 executed the falsifier through the actual connector path. A 6,983-byte raw application/json source was uploaded with conversion disabled, freshly downloaded, and reproduced the identical 6,983 bytes and SHA-256 fccf253ff35505fa7ffb8f01014c22678b9cf413ebd2027cb7ebd64d8d9fd331.


The raw-file path therefore passes and is adopted for future carrier publication.


2. AMENDMENT TO TRC-STANDARD-001 §5


The 90_MACHINE_READABLE_SUPPORT folder may contain the same logical carrier filenames already listed in §5, but every machine-readable carrier must be stored as a non-Google-native raw file.


Required MIME types:


- application/json for manifest.json, evidence_graph.json, link_validation.json, root_hash_receipt.json, frozen_register_rows.json, e3_reconstruction_receipt.json, validation_summary.json, and other JSON carriers;
- text/plain for checksums.sha256 and other line-oriented checksum or normalization records;
- another non-Google-native MIME type only when the standard or a numbered amendment explicitly defines its canonical raw-byte representation.


Conversion to a Google-native type must be disabled.


The embedded Base64-inside-a-native-Google-Doc carrier pattern is retired for all new capsule versions and successor carrier sets.


3. AMENDMENT TO TRC-STANDARD-001 §6


Machine-readable support carriers are governed by §6.1 Non-Google-native files.


Their identity is the SHA-256 of the raw bytes exactly as stored in Drive. Record:


- filename;
- immutable Drive ID;
- MIME type;
- exact byte count;
- SHA-256;
- retrieval date/time;
- upload receipt;
- immediate post-write download receipt;
- binary-equality result when a local or connector source reference exists.


Section 6.2 remains applicable to the four human-readable primary Google Docs and any other explicitly authorized native Google document. It no longer applies to machine-readable support carriers.


4. MANDATORY WRITE-THEN-READ TRANSACTION


A carrier publication is not successful when the create/upload call returns success. It is successful only after a fresh Drive round trip.


For every carrier:


1. Generate the exact canonical bytes before upload.
2. Compute expected byte count and SHA-256.
3. Upload as a raw file with conversion disabled.
4. Confirm the returned Drive MIME type and Drive ID.
5. Freshly download the new Drive object by that ID.
6. Compute observed byte count and SHA-256 from the downloaded bytes.
7. Require exact byte-count equality and exact SHA-256 equality.
8. Parse or validate the payload according to its declared format.
9. Only after all checks pass may the object receive its final carrier title, enter a manifest, be cited by a tracker/review request, or contribute to VALIDATION.


A failure at any step is WRITE-FAULT or ROUNDTRIP-FAULT. The object is visibly labeled failed, preserved in corrupted provenance, and excluded from all manifests and hashes.


5. NATIVE GOOGLE DOC DIAGNOSTIC RULE


Native Google Doc fileSize metadata is not a sufficient emptiness test.


TRC-COR-007 has a readable body and Drive-search content even though AO48 observed fileSize=1. Conversely, all seven v0.2 carriers were proven empty because get_document_text returned zero paragraphs and the manifest text/plain export was BOM-only.


For native Docs:


- fileSize may trigger an inspection warning;
- emptiness requires body retrieval or export evidence;
- authoritative checks are get_document_text, a declared export, and content/hash inspection—not fileSize alone.


This corrects only AO48-COR-026’s claim that TRC-COR-007 itself was empty. It preserves AO48’s v0.2 failed-publication conclusion and raw-carrier proposal.


6. PRE-MANIFEST GATE


A canonical manifest may reference only carriers that have passed the write-then-read transaction.


The manifest itself must first pass the same transaction before:


- ROOT_SHA256 is computed or accepted;
- checksums.sha256, root_hash_receipt.json, or validation_summary.json are generated;
- the capsule status moves from ASSEMBLY to VALIDATION;
- a package-level independent review becomes APPROVE-eligible;
- any Closure Log locator or root-hash entry is considered.


Dependent receipts must be generated from the actual freshly retrieved Drive IDs, raw bytes, sizes, MIME types, and hashes—not from intended local payloads or filenames.


7. TEST FIXTURES AND RECURRENCE CONTROLS


Retain TRC-WRITE-FALSIFIER-001 as a test fixture only. It is not an EC-020 carrier and receives no capsule evidence credit.


Every implementation or automation that publishes carriers must include tests for:


- empty payload rejection;
- MIME-type mismatch;
- byte-count mismatch;
- SHA-256 mismatch;
- JSON parse failure where JSON is required;
- accidental Google-native conversion;
- upload-success but fresh-download failure;
- duplicate or stale manifest inclusion;
- failed carrier title/index leakage;
- generation of root/checksum/summary before manifest round-trip PASS.


8. VERSION AND MIGRATION RULE


TRC-EC020-v0.1 remains ASSEMBLY/provenance with six reconstructable native-Doc carriers and one malformed manifest.


TRC-EC020-v0.2 remains failed-publication provenance only.


The next EC-020 publication attempt must use a new numbered capsule/carrier version and raw-file carriers. It must not silently overwrite or relabel v0.1 or v0.2.


Existing terminal mathematical records remain authoritative and are not migrated into a new truth source. The successor capsule remains an additive verification view.
