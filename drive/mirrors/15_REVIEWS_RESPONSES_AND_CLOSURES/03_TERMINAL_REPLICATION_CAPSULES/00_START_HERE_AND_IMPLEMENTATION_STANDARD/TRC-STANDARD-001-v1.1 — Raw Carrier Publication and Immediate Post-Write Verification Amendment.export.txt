1. INCIDENT BASIS


Two consecutive EC-020 machine-support publication attempts created seven one-byte native Google Docs rather than byte-bearing machine-readable carriers. TRC-COR-007-v1.0 records the v0.2 failure. AO48-COR-026-v1.0 independently confirmed all seven one-byte objects and proposed moving carrier publication to raw non-Google-native files.


This amendment converts that incident into a reusable publication rule. It does not validate, seal, or alter any capsule or Easy Closure.


2. REQUIRED CARRIER FORMAT


2.1 Default rule.
Every file in a 90/91_MACHINE_READABLE_SUPPORT folder MUST be stored as a raw non-Google-native Drive file when the connector or execution environment supports byte-preserving upload.


Use:
- application/json for manifest.json, frozen_register_rows.json, link_validation.json, evidence_graph.json, e3_reconstruction_receipt.json, root_hash_receipt.json, validation_summary.json and independent-review receipts expressed as JSON;
- text/plain for checksums.sha256 and normalization notes when plain text is the natural format.


2.2 Hash rule.
Raw carriers are governed by TRC-STANDARD-001 §6.1: hash the exact stored bytes. Record filename, Drive ID, MIME type, byte count, SHA-256, retrieval date and parent capsule/version.


2.3 Native-Doc fallback.
A Google Doc/Base64 carrier is permitted only when raw upload is technically unavailable. The fallback must be visibly labeled FALLBACK CARRIER, include explicit begin/end markers, canonical byte count, payload SHA-256, encoding and newline rules, and must pass an immediate fresh-read reconstruction before it may be indexed. Filename or title alone provides zero evidentiary credit.


2.4 No silent conversion.
A raw carrier must not be converted to a Google Workspace type. Any conversion changes the content-identity regime and requires a new numbered carrier revision.


3. IMMEDIATE POST-WRITE GATE


Before a newly created carrier is titled as VALIDATION, cited in a manifest, or used to generate a dependent hash, the publishing line must perform all of the following in the same execution round:


W1. Freshly retrieve file metadata and confirm the intended MIME type.
W2. Confirm a nontrivial stored byte size. A one-byte native Doc or an export containing only a BOM is an automatic WRITE-FAULT.
W3. Freshly retrieve the carrier bytes or declared fallback payload.
W4. Recompute byte count and SHA-256 and compare them with the pre-write values.
W5. Parse JSON carriers or validate checksum-file syntax as applicable.
W6. Record the post-write verification receipt before indexing the carrier.
W7. If any check fails, stop the publication attempt, label the object FAILED/UNUSED — DO NOT USE, preserve its Drive ID and history, and route it to CORRUPTED provenance. Do not build dependent manifests or root receipts from it.


4. VERSION AND DEPENDENCY ORDER


Machine-support publication must proceed in dependency order:


1. Generate canonical leaf payloads locally or in a byte-capable environment.
2. Hash and publish each leaf carrier.
3. Fresh-read and verify every leaf.
4. Generate manifest.json only from verified leaf identities.
5. Publish and verify the manifest.
6. Generate checksums.sha256, root_hash_receipt.json and validation_summary.json only from the verified manifest and leaf set.
7. Publish and verify those dependent carriers.
8. Open non-author capsule review only after the complete set passes post-write verification.


A failed attempt never supersedes the last reconstructable version merely by using a higher version number.
