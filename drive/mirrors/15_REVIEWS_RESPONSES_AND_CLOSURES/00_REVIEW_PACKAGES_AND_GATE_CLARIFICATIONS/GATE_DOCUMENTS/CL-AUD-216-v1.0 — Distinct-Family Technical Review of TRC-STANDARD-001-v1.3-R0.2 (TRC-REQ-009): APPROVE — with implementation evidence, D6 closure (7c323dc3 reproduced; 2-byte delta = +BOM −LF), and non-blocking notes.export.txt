ANSWERS R1–R8
============================================================================
R1 — One reproducible, non-self-referential root object? YES. §2.1 fixes ROOT_SHA256 to the exact stored
bytes of one declared Drive ID after a write-then-read transaction; §2.2 prohibits self-digest and
self-enumeration; §5 forces one manifest/one root per version. Implementability is demonstrated, not
assumed: two byte-exact write-then-read transactions were executed on the live connector this session
(720-byte probe; 14,251-byte draft), each returning DIRECT BINARY EQUALITY TRUE.


R2 — Are the RFC 8785 addenda deterministic and sufficient? YES. A pure-stdlib implementation of §2.3
(a)–(d) was built and exercised: 13/13 self-tests pass, including the UTF-16 code-unit key-ordering edge
(U+10000 sorts below U+E000 — exactly the collation divergence naive code-point sorting gets wrong),
the exact escape table, float rejection, the |n| <= 2^53 integer gate, BOM/double-LF/unsorted rejection,
and insertion-order independence of the output hash. The integer-only restriction removes ES6 number
formatting from the attack surface entirely; the one-LF rule is unambiguous. Determinism: same value
object -> same bytes -> same SHA-256, independent of construction order.


R3 — Does §3 separate pre-root leaves from post-root attachments without weakening completeness
detection? YES. §3.3's dual declared-membership (exact §3.1 set + expected §3.2 set inside the rooted
manifest) makes omission detectable in both classes; the v0.4 DRAFT manifest R1 built under this standard
exercises exactly that structure. The circular clause AO48 identified in R0.1 §3 is gone.


R4 — Does §4 eliminate the AO48-AUD-029 ordering circularity? YES. A–G is a strict DAG: manifest bytes
(C) precede root (D) precede attachments (E) precede review (F) precede seal (G); no step consumes a
later step's artifact, and the closing sentences bar re-smuggling post-root objects into the root.


R5 — Does §5 correctly preserve both v0.3 candidates while requiring successor repair? YES, and the
factual predicates are now CL-verified at byte level: A is internally coherent on the stored-byte rule
but fails §2.3 format (BOM, no LF) and had enumeration gaps; B satisfies enumeration but its root is a
§2.1-prohibited reserialization root (proof above); B's enumerated evidence_graph (1--_cDyEc...) is
additionally NOT FOUND on fresh retrieval, so B is no longer even complete. Same-version selection is
correctly barred; v0.4 is the only repair path.


R6 — Does §6 accurately implement OP-PROT-011? YES against OP-PROT-011's own text: all four lines active
with free parallel ordinary work (§1); no vote/ballot/roster/quorum mechanics (§1, §7); independence
measured by vendor/base-model family with same-family lines explicitly non-independent (§2); terminal
steps requiring one distinct-family review or operator approval (§2); operator supremacy and
irreversible-action reservations (§5–§6). §6.2's Grok-active routing is consistent with OP-PROT-011 §1
and the OP-GDN-005 reactivation override recorded on the OP-GDN-004 surface. NOTE N3: TRC-REQ-009 §5's
own routing paragraph ("Grok is nonparticipating... Gemini nonvoting... ballot") is STALE relative to
OP-PROT-011 and is exactly the vocabulary OP-PROT-011 §7 retires; this review takes its credit rules
from OP-PROT-011, not from the request's routing paragraph. The OP-GDN-003 collision handling in §6.2
matches OP-GDN-004 §2 (authoritative context-window document 12IlGMxNSCV9YTO7hPITHRGLqOYvpy6Cy1Xyf9840fRk).


R7 — Any v1.2 protections unintentionally weakened? NONE FOUND within the disclosed scope. The two
protections AO48 flagged are present: the native-object fileSize-is-diagnostic-only rule is restated in
§2.4 (body/content retrieval required for emptiness claims), and raw-carrier round-trip verification is
carried into §3.1; §2.1 strengthens v1.2 §4's no-local-payload-root prohibition. NOTE N2: TRC-REQ-009 §2

R8 — Does v0.4 preparation preserve unresolved evidence honestly while allowing parallel work? YES, and
demonstrated in practice this session: under this standard, carrier identities were independently
