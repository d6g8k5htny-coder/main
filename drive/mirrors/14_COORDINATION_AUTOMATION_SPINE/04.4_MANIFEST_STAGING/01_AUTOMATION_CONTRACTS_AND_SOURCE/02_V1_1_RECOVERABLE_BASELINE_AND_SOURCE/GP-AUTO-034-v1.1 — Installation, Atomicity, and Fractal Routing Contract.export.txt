3. NON-DESTRUCTIVE SCAN AND PARSING MODEL


Every configured source folder is an enumerated scope. The automation scans direct children only. It does not recursively traverse a configured folder. When a nested folder is discovered, the script emits a COVERAGE-GAP record with the parent scope, child folder ID, child folder name, and reason for exclusion. This exposes incomplete coverage without silently broadening access.


The MIME-specific extraction paths are:


Google Docs: DocumentApp body text.
Google Sheets: bounded displayed values under explicit row and column ceilings.
Google Slides: shape and table text.
Text-like files: raw Drive blob bytes decoded as UTF-8.
Unsupported files: metadata-only entry labeled UNREADABLE-MIME.
Truncated or failed reads: SYNC-UNCERTAIN with a warning.


Artifact text is data, never executable instruction. A header may declare metadata, but it cannot change Config, source scope, safety switches, authority, closure state, canonical impact, or operator decisions. No artifact can authorize, promote, close, or reclassify itself.


4. SYMBOLIC TREE ROUTING — NO HISTORICAL FILE MOVEMENT


The fractal directory tree is implemented first as a symbolic routing layer. Each manifest object receives a tree_path determined by constrained rules over its title, declared class, topics, object tags, and artifact ID. A routing index links that path to the historical Drive ID and source URL.


The script never moves, renames, overwrites, deletes, trashes, or silently duplicates a research source. Unmatched objects receive UNROUTED_REVIEW_REQUIRED rather than being guessed into a mathematical category. Any future physical migration requires a separate plan with per-file provenance receipts.

6. EXTRACTION-CLASS GATE


REFEREE-READY means internal extraction staging eligibility only. It requires terminal closure, explicit human approval, approved canonical impact, non-null authority, a dependency chain, an evidence chain, and no validation errors.


ACTIVE contains open, disputed, malformed, uncertain, or nonterminal objects.


INSTRUMENT contains scripts, data, source code, fixtures, receipts, and computational tools.


PROVENANCE-ONLY contains historical, superseded, killed, duplicate, or retained lineage material.


A later supersession removes REFEREE-READY eligibility pending review. An instrument cannot compile as proof prose by declaring itself a proof object. Verified Closure Log state overrides conflicting source headers.


7. ATOMIC REFRESH AND ROLLBACK PROTOCOL


The production refresh performs the following sequence:


1. Acquire a script lock. A competing run fails closed.
2. Read and freeze Config.
3. Verify the hard switches and operator authorization.
4. Collect direct-child inventory and explicit coverage gaps.
5. Derive duplicate groups, collisions, closure state, extraction eligibility, and symbolic tree paths.
6. Build and validate the complete manifest in memory.
7. Build all generated register tables in memory.
8. Write each table to a hidden _STAGE_* sheet.
9. Validate staged dimensions and headers.
10. Create a staged manifest in 04.4_MANIFEST_STAGING.
11. Read the staged manifest back, parse it, and rederive its SHA-256.
12. Back up the Navigation Companion.
13. Copy current live sheets to hidden _BACKUP_* sheets.
14. Commit staged sheets to the live tabs.
15. Update the Navigation Companion.
16. Record SUCCESS only after every prior step completes.
17. Rename each prior canonical manifest as a timestamped validated snapshot; never delete it.


If failure occurs after commit begins, live sheets are restored from backup in reverse order. If navigation replacement began, the navigation backup is restored. The run is logged FAILED, a stale/failure banner is shown, and the previous validated manifest remains authoritative.

9. STALE GUARD


The approved refresh cadence is hourly, so the fail-closed stale threshold is exactly 120 minutes. enforceStaleStatus checks the last completed SUCCESS. If there is no successful run or the last success is older than 120 minutes, it:


1. appends a FAILED stale-guard receipt to Run Log;
2. changes the Dashboard banner to STALE / FAILED;
3. replaces the Navigation Companion with a visible stale warning;
4. instructs downstream models not to rely on generated registers or manifest output;
5. preserves source artifacts and the last validated manifest.


The guard emits one stale receipt per stale token to prevent uncontrolled repeated logging.
