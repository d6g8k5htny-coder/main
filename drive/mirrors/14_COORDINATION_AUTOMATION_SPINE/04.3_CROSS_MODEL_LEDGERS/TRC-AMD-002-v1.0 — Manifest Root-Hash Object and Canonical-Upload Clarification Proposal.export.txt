1. MATERIAL AMBIGUITY


TRC-STANDARD-001-v1.2 requires canonical bytes to be generated before upload, exact postwrite equality, and a ROOT_SHA256 derived only after the canonical manifest is freshly retrieved and verified. It does not state in one explicit sentence whether ROOT_SHA256 is the hash of:


A. the exact verified raw manifest bytes stored in Drive; or
B. a second deterministic parse-and-reserialize byte string that may differ from the stored raw bytes.


Candidate A uses A. Candidate B uses B and reports a 9,409-byte stored manifest but a 9,407-byte canonical reserialization. The two candidates also use different leaf-designation models under the same capsule version. Same-line GP analysis cannot select between them as independent evidence.


2. PROPOSED ROOT-HASH RULE


Add the following binding text to the next numbered TRC-STANDARD revision:


ROOT_SHA256 is SHA-256 of the exact raw bytes of the canonical manifest file after that exact Drive ID has passed the write-then-read transaction. The manifest bytes uploaded to Drive MUST already be the canonical bytes. A parser/reserializer may be used only as a validation control and MUST reproduce byte-for-byte the stored manifest. If parse/reserialize output differs from the stored manifest by any byte, the manifest is noncanonical and receives zero root or sealing credit.


Consequences:
- no root may be based on a byte string that is not itself stored and freshly retrieved from the declared canonical manifest Drive ID;
- no trimming, BOM removal, newline repair, key sorting, whitespace normalization, or reserialization may occur only after retrieval and then silently define a different root;
- exactly one final LF, no BOM, UTF-8, recursively sorted keys, and compact JSON serialization must be applied before upload when JSON canonicalization is the declared manifest format;
- the observed stored bytes, expected bytes, and canonical-validation bytes must be identical.


3. PROPOSED LEAF-ENUMERATION RULE


The canonical manifest MUST directly enumerate every root-bearing leaf carrier with Drive ID, title, MIME type, byte count, SHA-256, evidence role, and status. Consolidated index carriers may be included as additional leaves, but may not replace direct enumeration of the four primary identities, every evidence carrier, the exact register export, native-export identity records, and all checksum or reconstruction receipts required by the capsule specification.


A same-purpose alternate carrier cannot be silently substituted. Each carrier must have one declared role. Superseded, collision, failed, or provenance-only objects must be listed outside the active root-bearing leaf set or explicitly tagged with zero root-bearing credit.


4. EFFECT ON THE CURRENT CANDIDATES


Candidate A:
- strength: its proposed root is the SHA-256 of exact freshly verified stored manifest bytes;
- unresolved defect under the proposed clarification: its six consolidated carriers may not directly enumerate every required primary/evidence identity at the canonical manifest level.


Candidate B:
- strength: more direct and granular enumeration;
- defect under the proposed clarification: the claimed root is computed from a 9,407-byte reserialization rather than the 9,409 exact stored manifest bytes, so the stored file is not the canonical byte object being hashed.


Therefore neither current candidate should be selected automatically. The conservative repair is a successor capsule version, provisionally TRC-EC020-v0.4, combining:
- Candidate B’s direct enumeration discipline;
- Candidate A’s stored-byte root discipline;
- one canonical pre-upload serialization;
- exact postwrite byte equality;
- one manifest Drive ID and one accepted root candidate;
- no alternate same-version root bundle.
