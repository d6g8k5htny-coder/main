2. CAUSE


C1  The first-entry session used read_file_content, which returns a RENDERED
    natural-language representation of a Google Doc. That endpoint's own
    documentation states the representation "will change over time." It is
    therefore structurally unfit for byte-identity adjudication, and its output
    carries injected backslash escaping and flattened paragraph structure.


C2  download_file_content with exportMimeType = "text/plain" was NOT TESTED in
    the first-entry session. It was available the entire time.


C3  A tool-selection error was generalized into an architecture-wide
    impossibility claim, and a large migration was recommended on that basis.
    The correct scope of the original observation was: "this session used the
    wrong endpoint."


C4  THE DEEPEST CAUSE, AND THE ONE WORTH FIXING. A binding retrieval standard

4. THE CORRECT CONCLUSION


  4.1 Native Google Docs MAY serve as frozen-body carriers, provided the freeze
      policy specifies a reproducible export and a line-anchored extraction
      procedure. OP-PROT-017 is that procedure and it works.
  4.2 Rendered connector text is NOT an acceptable byte-identity source, ever.
  4.3 Raw uploaded files round-trip byte-exactly, including CRLF, bare LF, tabs,
      trailing spaces, NFC/NFD distinctness, and the final newline. Verified this
      run against _PROBE_bytes_20260728.txt (1of2xRi8dW0Sgspli0w82gvsZK_tco7Nu,
      113 bytes, SHA-256
      d43f5643ce745f886dfe507d14f90078afcc223910db61fec7c1128fe8ff4bf9).
  4.4 The existing carrier architecture is NOT invalidated. No migration is
      required. No object needs re-export.
  4.5 Existing exact-hash work remains executable.
  4.6 PILOT-001 obligation R0 is technically executable using the approved
      method. The eligibility bar on PILOT-001 (orientation-order exposure)
      is UNAFFECTED by this erratum and still stands on its own.
  4.7 P02-LM-006 was never blocked by a carrier defect. It is blocked by the
      absence of an eligible reviewer, which is a different and real problem.


  4.8 A NEW AND SEPARATE LIMITATION, MEASURED THIS RUN. Conversion INTO a Google
      Doc is lossy: tabs become 8 spaces and blank lines are doubled. Trailing
      spaces, NFD sequences, ASCII quotes and Unicode math survive. Therefore
      Docs are fine for prose and proof bodies authored in Docs, and are NOT fine
      for source code, TSV, or any format whose semantics depend on tabs or exact
      blank-line structure. Those require raw carriers. See FS2-CANARY-001
      section 4 for the measurement. This does not resurrect the retracted claim;
      it bounds a different one.

What this does and does not show:


  IT DOES NOT SHOW a uniform model or provider defect. One session of the same
  model that failed on 2026-07-28 had already succeeded on 2026-07-27. The
  capability was present in the lineage.


  IT DOES SHOW that correct method knowledge lived in a legacy artifact
  (OP-PROT-017) that Fresh Start 2.0 never imported, so it propagated to some
  sessions and not others by accident of which folders a session happened to
  read. Two of three sessions did not find it. That is an ARCHITECTURAL
  propagation failure, not a model failure, and it is fixable by importing the
  standard and gating on a canary.


  IT ALSO SHOWS a live instance of correlated tool-selection bias: two
  independent Anthropic sessions, with no contact, reached for the same wrong
  endpoint and drew the same wrong conclusion with the same confident wording.
  Had a third Anthropic session been asked to "corroborate" the finding, the
  likely outcome was agreement, and the agreement would have been worth nothing.


  CONSEQUENCES, BINDING:
    - The two sessions in agreement on the false claim are NOT independent
      merely because they occurred separately, on different days, in different
      threads. They shared a provider lineage and a tool-selection prior. VUL-010
      applies to negative findings exactly as it applies to positive ones.
    - Exposure and method declarations are necessary but not sufficient. Both
      wrong sessions would have declared their method honestly; neither would
      have known it was wrong.
    - Only an executable check against known bytes distinguishes the correct
      method from the incorrect one. Verbal confidence did not, in three
      documented attempts.
    - Therefore: FS2-CANARY-001 is mandatory before any exact-hash claim, and a
      capability declaration without a canary result is void.
