# CONTROL_PLANE_PROTOCOLS.md


## Admission transaction


1. Reserve `DRAFT_ID`.
2. Hash raw bytes.
3. Parse claims.
4. Split non-atomic uploads.
5. Resolve dependencies.
6. Execute hostile checks.
7. Obtain independent review.
8. Freeze exact body.
9. Write promotion decision.
10. Copy—not move—into Core during the initial 2.0 migration period.
11. Verify destination manifest.
12. Only then mark the candidate promoted.


## Concurrency


Reservations are create-only atomic records. A reviewer without register-write capability must create a reservation file before work. Duplicate reservations are reconciled by exact object ID and timestamp; they do not earn extra independence credit.


## Amendments


Never edit a frozen body in place. Create a numbered successor, preserve the predecessor, and record the supersession edge.


## Automation boundary


The supplied scripts are dry-run/control-plane implementations. No hourly cron or webhook is active merely because the files exist. Scheduling requires an explicit supported automation and an auditable execution account.




## Mathematical preparation transaction
A DRAFT_ID transaction must include DRAFT_MANIFEST.json, exactly one raw_upload, parsed_claims.json, dependency_sniff.txt, domain_declaration.json, power_ledger.json when applicable, vulnerability_scan.json, review_exposure.json, hostile-review records, and promotion_decision.json. The DRAFT template is copied; the template itself is never used as a live candidate.


The preparation result is only a disposition proposal. `PROMOTION_READY` means the intake package is complete enough to enter the formal promotion gate; it does not mean `CORE`.


## Integrity-gate order
Run gates in this order:
1. exact identity and extraction rule;
2. atomicity;
3. law and coordinate firewall;
4. domain lattice;
5. dependency/interface closure;
6. symbolic power ledger;
7. vulnerability scan;
8. hostile attacks and mutation controls;
9. reviewer eligibility classification;
10. reproducibility and state-surface readback.


A later PASS cannot repair an earlier NO without a numbered correction or successor.


## Review-count correction
The historical heuristic “three surviving hostile reviews” is not sufficient for Core admission. Surviving attacks are evidence; eligible independence depends on authorship, target exposure, provider lineage, implementation ancestry, method class, exact-hash reproduction, negative controls, and relevant vulnerability history. The live Reviewer Eligibility table controls.


## Standing authorizations
Standing authorization permits execution and bounded status transitions only within its exact class. It never changes a theorem outside its declared scope, overrides a red promotion gate, authorizes destructive migration, or grants external release. Every use records the authorization ID and exact predicate satisfied.


## Promotion write transaction
1. Freeze the proposal and dependency snapshot.
2. Evaluate PG-01 through PG-10.
3. Abort on HOLD/NO unless the proposed result is explicitly conditional and the standing rule permits it.
4. Prepare all registry, manifest, closure-log, and pointer writes before execution.
5. Execute in a bounded transaction.
6. Read back every changed surface.
7. If any surface disagrees, roll back or publish a correction record; do not leave a partial promotion.
8. Record reopen conditions and downstream/non-effect language.


## Migration transaction
Migration uses MIGRATION_PROTOCOL.md. During the parallel period, copy or point; do not move legacy sources. A new current-state snapshot of a previously unhashed object requires its own review and does not inherit historical exact-hash approval.


## Evidence transaction
Every experiment begins from a preregistration and object card. Raw outputs, derived results, seeds, environments, and replication receipts remain separated. Empirical results may trigger a correction, falsifier, or new candidate, but cannot directly edit a Core proof or theorem status.


## Scheduler boundary
The existence of extract_claims.py, prep_agent.py, AUTO_SORTER_LOGIC.py, or a registry does not create an hourly job. Until an auditable supported scheduler is explicitly installed, ingestion is manually or agent-triggered and every run receives a timestamped receipt.
