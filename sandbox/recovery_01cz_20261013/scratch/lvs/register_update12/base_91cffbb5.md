## 1. What "verified in Lean" can and cannot mean here

The lane separates five questions (guide §"One proof, several separate questions"). Only the
third is answered by Lean:

| Question | Answered by | Label |
|---|---|---|
| Are these the intended bytes? | repository + commit + path + SHA-256, bound in a manifest | — |
| What is the formal statement? | a Lean declaration whose docstring quotes the informal anchor | `specified` |
| Does the proof establish that statement? | pinned build + `leanchecker` + transitive axiom audit + negative controls, in a trusted run | `proved` at source, `kernel-checked` only in a run receipt |
| Is the formalization faithful? | an independent statement/alignment review (different provider, family and agent) | `PENDING_INDEPENDENT_REVIEW` until one exists |
| May the scientific claim be promoted? | the existing controlling acceptance machinery | never by this document |

Formal-progress labels are exactly `none`, `specified`, `proved`, `kernel-checked`. In the ladder of
work item #95 (GitHub issue, closed 2026-09-27) (L0 prose … L5 proof-assistant checked), a target with a trusted
`kernel-checked` receipt is L5 evidence **for exactly that target**; a `specified` statement is not
evidence of truth at all — it is a precise question. Allowed transitive axioms of every proof:
`propext`, `Classical.choice`, `Quot.sound`. `sorryAx`, `Lean.ofReduceBool` (`native_decide`) and
custom axioms are refused by every gate. Unformalised parents enter as explicit hypotheses or as
fields of interface structures, never as axioms.

Three things follow, and the claim table below is read with them in mind:

1. **A statement is not a proof.** The new statement-only package (§3.6) moves a claim's formal-progress
   label from `none` to `specified`, a label about the existence of a Lean sentence, not about the
   claim's status; it proves nothing. Its value is that each informal theorem now has one exact
   Lean sentence that an independent reviewer can compare with the source and that a future
   prover can target.
2. **An arithmetic skeleton is not the theorem.** The integer identities on `main`
   (§3.1; `proved` at source, `kernel-checked` only where a trusted receipt exists) establish the
   displayed numbers, not the analysis around them. A claim whose skeleton is
   kernel-checked stays `none` or `specified` as a claim.
3. **Nothing here is reviewed.** Every Lean object in this programme is author-side until a
   reviewer with a different provider, family and agent records an alignment through the
   existing validators (`tools/formal_gate_check.py --alignment`, Math- `formal/gate.py --alignment`).

### 2.3 Mathlib: cache or source

Every Mathlib-dependent package here (`Math-` `formal/`, the companions, `CapFirstExit`, the new
specifications packet) is built with the Mathlib olean cache:

```sh
cd <package dir>           # e.g. Math-/formal
lake exe cache get         # needs https://cache.mathlib.org (Mathlib's olean cache)
lake build
```

Hosts a build machine must reach: `github.com` (git clones, release assets), `raw.githubusercontent.com`
(elan script), `release.lean-lang.org` (toolchain downloads via elan), `cache.mathlib.org` (Mathlib
olean cache; `lake exe cache get` fails closed without it), `reservoir.lean-lang.org` (Lake's
package index, consulted on `lake update`; not needed for a locked build). GitHub-hosted CI reaches
all of them; `lean-action` restores the cache in minutes.

## 3. Packages, gates, receipts

self-awarded labels without running Lean; in execution mode it rebuilds from scratch, runs
`leanchecker`, audits `#print axioms` for every target, executes negative controls that must fail,
and writes a receipt. A receipt is evidence for exactly the targets it names at the commit it names.

SHA-256 of every bound file; toolchain and lock; the root module imports exactly the registered
modules; no `sorry`, `native_decide` or `axiom` outside comments; the target inventory equals the
`theorem` declarations in order; every informal anchor is a verbatim substring of its byte-pinned
source; every package file is bound or declared unbound; `ALIGNMENT.md` matches the manifest. With
`--run-lean`: fresh `lake build`, `lake env leanchecker UniversalLaw`, `#print axioms` for every
target restricted to the three allowed axioms, elaborated types, the manifest's textual mutation
controls (each must fail in Lean), the `sorry` / imported-axiom / `native_decide` controls (each must

their differences are recorded in [docs/agents/LEAN_AUDIT_OWNER.md](agents/LEAN_AUDIT_OWNER.md).

The statement-register gate (3.6) additionally refuses any `theorem`, `lemma`, `example`,
`instance`, `axiom`, `opaque`, `unsafe`, `partial`, `macro` or `set_option` in the packet, requires
every top-level `def … : Prop` and `structure` to be registered in `REGISTER.json` (and vice
versa), requires every anchor to be verbatim in the pinned bytes under `sources/`, and refuses a
register row or receipt that says `proved` or `kernel-checked`: a statement package cannot
self-award a proof label.

## 4. The statement register

`specifications/lean_statements_20261010/REGISTER.json` (Math-) lists every registered mathematical
claim of the programme with: the byte-pinned Layer 0 source (repository, commit, path, bytes,
SHA-256), the transcribed LANDING_CLAIMS disposition where one exists (never re-derived), the Lean
statement(s) that specify it, their formal-progress label, what is not established, and the next
step toward a proof. The rendered table:

Column key. **Claim**: the register `claim_id`. **Layer 0 source**: `commit:path` of the byte-pinned source under `sources/` in the packet (SHA-256 and byte count are in `REGISTER.json` `sources[]`), followed by the heading the row anchors to; *not pinned* means the row has no pinned bytes in this packet and therefore no Lean statement. **Transcribed disposition**: verbatim from `LANDING_CLAIMS.json`, `—` where the source carries none; it is never re-derived. **Lean statement(s)**: `Module.Declaration` in namespace `UniversalLaw.Spec` of the packet, all at `specified`; `main:` prefixes a theorem of the `main` core-Lean package `formal/` listed beneath the claim with its own `proved` manifest label (an arithmetic skeleton, never the claim). **Formal progress**: the claim-level label; no claim is `proved` or `kernel-checked`. **Not established** and **Next step** are abridged here to their first sentence; the full fields in `REGISTER.json` and the packet's `SCOPE.md` are the authoritative text and are longer, not shorter, in what they exclude. Alignment of every statement with its anchor is `PENDING_INDEPENDENT_REVIEW`.
