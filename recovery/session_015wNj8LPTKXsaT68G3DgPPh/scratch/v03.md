## Identity model
Keep four identities distinct:
1. Stable logical work/object ID, using established namespaced IDs and explicit alias/successor crosswalks
2. Content/source occurrence identity: repository, full commit for retrieval, path, packet-tree OID where available, exact file inventory and manifest digest, consumed contracts/selectors and external dependency versions
3. Presentation identity: surface ID/version, route or selector, renderer/config/generator identity and relative-link context
4. Execution/integration identity: source head, current base/tested merge and parents, workflow/run/attempt, deployed build and observed asset/config hashes

Path membership is not durable work identity. Existing version suffixes must not be stripped heuristically. Support evidence-backed typed corrected-by and supersedes edges across distinct comments/objects, including the amendment and author acknowledgment chain; never infer a mathematical correction or acceptance from a merely newer timestamp. Packet-tree equality cannot cover consumed sources or workflow inputs outside that directory. Identical copied files can share content custody/cache only after exact-byte and provenance checks; each occurrence and consuming work object remains distinct. A source revision marks declared copies/consumers for assessment without silently repinning historical copies or inventing changed copy bytes.

Native comment sources need provider object ID, public URL, observed time, exact body digest and extraction rule. A link to a mutable comment is not an immutable copy. Capture the exact immutable consumed bytes and bind every consumer-recorded digest to that capture. If polling missed an intermediate revision or a consumer names an unavailable digest, coverage stays unresolved. Matching polls or a recurring digest cannot prove absence of unseen edits; updated_at cannot reconstruct history.

## Release records

Receipt-storage commit differs from the build it attests. A later metadata-only receipt commit may trigger Pages; do not claim it verifies itself. The chosen storage/build arrangement must either exclude receipt-only commits from deployment or demonstrably preserve the covered asset/payload vector so prior evidence is reusable. Receipt-only changes must not generate an endless chain of purported new verified releases; otherwise finalization remains blocked. Release-chain advancement must atomically fence the expected predecessor using a supported expected-old-ref/compare-and-swap or equivalent validated fail-closed mechanism. Recheck the valid release claim, expected predecessor, source/test vector and deployed identity at finalization; lease rows alone are not a lock. Two candidates for one predecessor cannot both advance the baseline or consume a slice. The losing candidate is retained as superseded/uncommitted evidence. A baseline guard alone does not fence deployment activation: a losing candidate that was actually deployed is recorded as observed-live/uncommitted, and Public now becomes unverified wherever its served vector differs from a committed receipt. Finalization requires guarded activation or explicit reconciliation of that race. If the publishing route cannot supply the guard, finalization remains blocked rather than simulating atomicity. Reuse prior deployed evidence only after an explicit equality check of the covered asset/payload vector. Corrections, rollback and retractions append successor records.
