## Identity model
Keep four identities distinct:
1. Stable logical work/object ID, using established namespaced IDs and explicit alias/successor crosswalks
2. Content/source occurrence identity: repository, full commit for retrieval, path, packet-tree OID where available, exact file inventory and manifest digest, consumed contracts/selectors and external dependency versions
3. Presentation identity: surface ID/version, route or selector, renderer/config/generator identity and relative-link context
4. Execution/integration identity: source head, current base/tested merge and parents, workflow/run/attempt, deployed build and observed asset/config hashes

Path membership is not durable work identity. Existing version suffixes must not be stripped heuristically. Packet-tree equality cannot cover consumed sources or workflow inputs outside that directory. Identical copied files can share content custody/cache only after exact-byte and provenance checks; each occurrence and consuming work object remains distinct. A source revision marks declared copies/consumers for assessment without silently repinning historical copies or inventing changed copy bytes.

Native comment sources need provider object ID, public URL, observed time, exact body digest and extraction rule. A link to a mutable comment is not an immutable copy. Capture the exact immutable consumed bytes and bind every consumer-recorded digest to that capture. If polling missed an intermediate revision or a consumer names an unavailable digest, coverage stays unresolved. Matching polls or a recurring digest cannot prove absence of unseen edits; updated_at cannot reconstruct history.

## Change classification and impact
Observe bounded changes from explicit per-source checkpoints. A change ID binds the target, before/after identities, event kind and causal occurrence (provider revision/event token or observed predecessor). A→B→A→B is a fresh recurrence, while duplicate delivery of the same observed occurrence is idempotent. Poll time alone does not create a change. Track available update/revision metadata even when content bytes recur; changed metadata can require reconciliation rather than a silent no-op. Conflicting reuse of one occurrence ID fails.

Classify changes along separate content, mathematical-contract, dependency-disposition, execution, presentation and provenance dimensions. Prove unchanged reviewed bytes/hypotheses/alignment/consumed contracts/execution inputs before calling a delta base-only or provenance-only. Commit subjects, equal executable/output bytes, AST equivalence and passing transition audits alone are insufficient. Mathematical prose is not exempt because it lives in NOTE.md; current_required is an edge/control change until assessed.

The existing transition audit's input_graphs_unchanged expresses nonmutation, not old/new graph equality. Its check_passed bounds mapped controlling failures; it is not a global semantic-equivalence certificate. Use actual diff/coverage/impact output and direct relevant-slice comparison. The already-resolved Math#231 smooth-versus-real-analytic amendment is a regression example: unchanged code/output did not imply unchanged claim scope.

Traverse union(old edges,new edges) and typed presentation consumers. Dependency disposition changes create impact events even if consumer bytes are unchanged. Preserve contrary source-bound findings through merges: merged status, an older/narrower PASS or green CI cannot erase an unresolved AMEND. Reuse prior reviews only for unchanged exact scope; integration checks bind the actual current tested commit, including the actual checked-out PR merge ref where applicable, rather than relying only on the head under which checks are listed. Unknown impact remains visibly pending.

## Release records
Use two small append-only record types in main, proposed under docs/site/releases/ subject to final path/recursion validation:
- Manifest: release/predecessor IDs, source-cut vector, selected policy and generator versions, work/source/presentation identities, consumed change-slice IDs, route contracts, dependency prerequisites, exclusions/deferments and intended coverage
- Completion receipt: manifest digest, actual deployment/build and asset/config identities, observed public URLs/journeys, outcome, verification scope (exhaustive, structural or sampled), checked_at and exact evidence links

An outer manifest can bind SOURCE_FILES.json; avoid self-containing hashes. Freeze manifest, validate/test, deploy, observe live, then persist receipt. Receipt-storage commit differs from the build it attests. A later metadata-only receipt commit may trigger Pages; do not claim it verifies itself. Release-chain advancement must atomically fence the expected predecessor using a supported expected-old-ref/compare-and-swap or equivalent validated fail-closed mechanism. Recheck the valid release claim, expected predecessor, source/test vector and deployed identity at finalization; lease rows alone are not a lock. Two candidates for one predecessor cannot both advance the baseline or consume a slice. The losing candidate is retained as superseded/uncommitted evidence. If the publishing route cannot supply the guard, finalization remains blocked rather than simulating atomicity. Reuse prior deployed evidence only after an explicit equality check of the covered asset/payload vector. Corrections, rollback and retractions append successor records.

## What Public now means
Report the exact object-version/surface-version at an observed deployed build, with live verification context and checked_at. This is an as-of observation, not a perpetual guarantee. When a different live build or covered asset vector is observed without a matching receipt or proven equivalence, current publication coverage becomes unverified; retain the old receipt as historical evidence. Out-of-pipeline deployments and rollbacks are events. No successful old receipt can silently cover an unobserved successor. Representation and verification are separate axes:
- Representation: canonical source, indexed Library entry, exposition, interaction, download
- Verification: generated/local, hosted checkout, actual live deployment

A merged PR, link, catalog row or localhost smoke test is not live-route evidence. Sampled UI checks must be labeled sampled; structural membership/link validation must not be described as every individual source being browser-opened. Source availability, integration, scientific acceptance and publication completion remain separate. Conditional work may be truthfully public while its exact disclosed premise remains unmerged or unaccepted.

Use the historical main#239 completion receipt as a bootstrap candidate after current live reconciliation. It does not establish the pending e321c8f candidate is deployed.

## Exact queue consumption and failure rules
The unit consumed is (change ID, affected object version, surface ID/version, verification contract), not the entire mutable queue or a repository HEAD.
- Freeze the intended slice set and source-cut vector
- Verify required publication prerequisites from either a compatible prior verified receipt or this release
- Acknowledge only the exact successful slices; an event remains pending while any required surface is outstanding
- Deferred/excluded slices retain explicit reasons and do not masquerade as publication; they can be dispositioned separately without becoming verified
- Live reachability can be recorded even for a conditional/defective mathematical source, but does not clear its review/readiness obligation
- Failed deployment consumes no slices; partial route failure leaves those surfaces and actual dependents pending
- Unrelated successful surfaces need not wait for another packet's long replay
- New changes after freeze remain queued; stale expected head/build/vector requires reconciliation, never overwrite
- An optional broken citation can be a separate link-repair obligation rather than blocking unrelated scientific scope
- No race or successful merge silently removes contrary findings
