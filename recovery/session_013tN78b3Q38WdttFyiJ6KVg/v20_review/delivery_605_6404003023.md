### HIGH

**G1-F1. The journal writer and reader frame records differently, so one valid record makes the journal permanently unloadable.** `engine/conductor.py:24` and `:163`.
- **Writer.** `canonical()` uses `json.dumps(..., ensure_ascii=False)`. It escapes only characters below U+0020, so U+0085, U+2028 and U+2029 are written raw. `Journal.append` writes the record and fsyncs it (188-194).
- **Reader.** `_load` runs `raw.decode('utf8').splitlines()`, which also breaks lines at those three code points. The fsynced record is cut into fragments and `json.loads` raises `JSONDecodeError`, a `ValueError`.
- **Effect.** Every journal operation calls `_load`: `append`, `since`, `_replay` and `Coordinator.__init__`. After one such record the service cannot start, and freeing anything does not help.
  - The class docstring (122-126) says a truncated or malformed journal fails closed. Here a well-formed one does.
  - **The proof conductor's own journal** (`proof_conductor.py:310`) is exposed in the same way, the critic found. `claim()` checks `agent_id` only with `_text` (133-136, 567): any non-blank string of up to 128 characters. A `TASK_CLAIMED` whose `agent_id` contains U+2028 therefore makes that journal unloadable. This extension went through no refutation pass.
    - Its reach is narrower. In members read only as context, the server pins `agent_id` to `local-owner` and the runtime uses `frontier:<job>`. That leaves direct library callers.
  - The same class also backs `collaboration.py:202`, `intelligence.py:120` and `frontier_runtime.py:83`. Those files are not reviewed here. I make no claim about how their inputs reach it.
- **Scenario.** An agent drops an inbox proposal whose `actor` is `"agent\u2028x"`. `propose` checks only that the actor is a string of 1–120 characters (424). `PROPOSAL_CREATED` is committed, and every later load raises. Other routes in are `event_id` over HTTP (180), a decision actor, `worker_id`, and error text recorded as a reason.
- **Reproduced** without the carrier, by re-implementing the two lines with the stdlib:

  | Character in a payload string | Lines on read | Load |
  |---|---|---|
  | U+0085, U+2028, U+2029 | 2 | `JSONDecodeError` |
  | U+000B, U+001C, LF | 1 | loads (JSON escapes them) |

- **Fix and repair** (options for the owner):
  - Split on the LF byte before decoding, `raw.split(b'\n')`. `formal_queue.py:124` already splits bytes and is not affected.
  - Do not change `canonical()`: that would change the hash of every stored non-ASCII event.
  - An affected file can be repaired by replacing each raw separator with its `\uXXXX` escape. The hash chain stays intact, as `g1_linesep_fix_check.py` shows.
- **Tests.** No carrier test uses these characters. The engine tests were not delivered.

### MEDIUM

**G1-F2. An exception in the idle branch silently ends every coordinator worker thread.** `engine/conductor.py:662-672`.
- **Defect.** `_worker` calls `recover_jobs()` (666) and `snapshot()` (667) outside any try, and the append in the handler (671) can raise too. Any exception there ends the thread. Nothing records it or restarts the thread, and `start()` returns early while `started` is true (689).
- **Scenario.** A transient EMFILE hits the opening of `.journal.lock`, or an ENOSPC hits `publish_snapshot` in `recover_jobs` (that one needs an expired lease). Each worker thread exits on its next idle poll, 0.2 s later. HTTP still serves state, but automatic processing stops; only a manual `/api/check` or CLI `check` still runs jobs. A journal broken by G1-F1 has the same effect.
- **Tests:** none.

**G2-01. Replay recomputes completions from a tree the worker can write, so one damaged artifact makes the proof conductor unreadable.** `proof_conductor.py:476-478, 657-659, 696-698, 719-721, 746-749`.
- **Defect.** `_read` re-validates every `SCALAR_PILOT_COMPLETED` against `receipt.json` and the `project/` tree on disk. Only a blocked backend or a stale profile degrades to a per-completion state. Every other mismatch raises out of `_read`: a missing or oversized receipt, a profile-key mismatch, an invalid verification, a changed tree hash, or more than 32 files.
- **Scenario.** After claim X completes, `receipt.json` is deleted, or one file is added under `artifacts/claim-X/project/`. This can be done by the worker, by operator cleanup, or by a partial copy of the workdir. `ProofConductor(workdir)` then raises in `__init__` → `snapshot` → `_read`.
- **Tests.** Test 455-470 copies only an intact tree.

**G2-02. The journal-size guard undercounts, so it can admit the append that makes every later read fail.** `proof_conductor.py:541-546` against `415-417`.
- **Defect.** The pre-append estimate at 544 is `len(str(payload).encode('utf8'))`, the Python repr of the payload alone. `Journal.append` writes canonical JSON of the whole envelope plus a newline (`engine/conductor.py:188-193`). The read guard at 416-417 then rejects the oversized file on every read.
- **Model** (`g2_bytebound.py`, re-implemented canonical JSON):
  - A `TASK_CLAIMED` event is undercounted by 230 bytes.
  - Evidence `{'r': '"'*15000}` is undercounted by 15,205 bytes, because a quote is 1 byte in the repr and 2 in JSON.
- **Tests.** None exercises `MAX_JOURNAL_BYTES` or `MAX_EVENTS`.

**G2-03. The only "false receipt" test is caught early, so the checks that stop a failed verification being recorded as a completion are unpinned.** `test_proof_conductor.py:622-629`; code at `proof_conductor.py:666-667, 696-698, 715-724`.
- **Defect.** The test's receipt has no `project/` directory, so the tree check at 666-667 rejects it with a message the test's regex already matches. No test reaches these checks:
  - the live-mode raise for an invalid native verification (719-721);
  - the receipt profile-key check (696-698);
  - the downgrades for a backend or receipt that changed during replay (715-724).
- **Mutation reasoning** (static). Delete 719-721 and the suite stays green. `complete_claim` then records a completion with `verification.valid=False`, and `_validate_claim:504` blocks that pilot task for good.

**G3-F1. Any non-journal exception ends the only formal-queue worker, and the queue never drains again.** `formal_queue.py:305-329, 397-406`.
- **Defect.** `_worker` catches only `JournalError`. An `OSError` from `_claim`, which sits outside the try (306), or from the fallback `_complete` (326) ends the thread silently. `start()` respawns only when every thread is dead and someone calls it again. `workspace.py:65` calls it once, with `max_workers=1`.
- **Scenario.**
  1. The disk is briefly full during `attempt_dir.mkdir`, `_sync_directory` or `_append` (279-288).
  2. The worker thread exits.
  3. Disk space returns, but nothing restarts the thread.
  4. `enqueue()` keeps answering `queued`, and nothing ever runs.
- **Tests:** none.
