## Identity model
Keep four identities distinct:
1. Stable logical work/object ID, using established namespaced IDs and explicit alias/successor crosswalks
2. Content/source occurrence identity: repository, full commit for retrieval, path, packet-tree OID where available, exact file inventory and manifest digest, consumed contracts/selectors and external dependency versions
3. Presentation identity: surface ID/version, route or selector, renderer/config/generator identity and relative-link context
4. Execution/integration identity: source head, current base/tested merge and parents, workflow/run/attempt, deployed build and observed asset/config hashes

Path membership is not durable work identity. Existing version suffixes must not be stripped heuristically. Support evidence-backed typed corrected-by and supersedes edges across distinct comments/objects, including the amendment and author acknowledgment chain; never infer a mathematical correction or acceptance from a merely newer timestamp. Packet-tree equality cannot cover consumed sources or workflow inputs outside that directory. Identical copied files can share content custody/cache only after exact-byte and provenance checks; each occurrence and consuming work object remains distinct. A source revision marks declared copies/consumers for assessment without silently repinning historical copies or inventing changed copy bytes.

Native comment sources need provider object ID, public URL, observed time, exact body digest and extraction rule. A link to a mutable comment is not an immutable copy. Subject to the privacy-screening and authorized-custody rules below, capture the exact immutable consumed bytes and bind every consumer-recorded digest to that capture. A capture that cannot safely be retained stays blocked/unavailable; do not publish private data to satisfy an identity rule. If polling missed an intermediate revision or a consumer names an unavailable digest, coverage stays unresolved. Matching polls or a recurring digest cannot prove absence of unseen edits; updated_at cannot reconstruct history.

This does not extend to unrelated private information or create new standing permission; re-evaluate against current permissions when acting. A public source or old capture is not blanket permission to propagate unrelated/private material or secret-bearing payloads.

If an accepted record contains material requiring removal, stop further exposure and treat the affected projection as unresolved while remediation is arranged. Public projections must not contain private custody identifiers, access-key URLs or private CI-log contents.

Preserve the scientific disposition and the fact/reason of the recovery. Redacted bytes receive a new identity; they are never relabeled with the removed record's digest. Verify the authorized current-tree remedy and a valid successor checkpoint under the same nonauthor reconciliation review. Recovery does not restore verification by itself: any required evidence that cannot safely remain available stays unavailable/unverified until a valid authorized replacement satisfies the exact contract. Preserve the historical scope of what was actually verified without transferring it to changed bytes. The proposal does not itself authorize purging those residual copies.

## Supported logical finalization protocol
Use existing protected PR integration into main; do not invent an expected-old field in github_update_ref, bypass branch protection, create a new persistent credential, or assume the PR-head merge guard also locks the deployment.

The canonical accepted receipt chain is a deterministic fold of the verified main first-parent commit sequence from one frozen trusted checkpoint. Each first-parent commit is a **logical ledger boundary**, not a claim that it was a separate atomic PR or deployment operation. Bind the repository, full anchor commit, accepted predecessor, consumed-slice state, coverage, schema/validator policy and retained record identities in that checkpoint. A later validator version must not silently reinterpret historical winners. Every authoritative projection reproduces acceptance from the actual pinned history; merely merging a receipt or displaying its claimed outcome never acknowledges slices. A cache binds the evaluated main commit, checkpoint, validator/policy version and record digests. Cached current-release pointers and queue views are reproducible outputs, never independent mutable authority.

At each boundary:
1. Validate ancestry and compare the immutable receipt/manifest tree with the preceding boundary. Read every relevant intermediate first-parent path delta, not only the checkpoint-to-tip endpoint diff: edits/deletions/restorations can cancel out at the endpoints. No candidate means no advancement. A changed/deleted accepted record, missing checkpoint/ancestry, unsupported topology or uninterpretable record makes the fold unresolved and prevents further acknowledgment; retain the last valid prefix as historical evidence.
2. Validate the exact new candidate, its stored evidence, manifest digest, expected accepted predecessor, unique slice IDs, source/presentation/contract identities and compatible prerequisite closure. Its applicable current tested integration checks and owner claim remain required; a fold is not a review or CI waiver.
3. At most one unambiguous valid successor may advance at that boundary. Multiple competing candidates introduced together fail closed. An otherwise well-formed later sibling naming an already superseded predecessor is retained with a stale-predecessor/uncommitted reason and consumes nothing. A candidate overlapping already acknowledged slices likewise consumes nothing; exact duplicate delivery is idempotent, never a second advancement.
4. The next valid successor must name the actual accepted predecessor and use a newly reconciled frozen source/deployment cut. Never rebase, merge or re-label a losing candidate as if its old transaction won. A substantive amendment is a new candidate with its own evidence.

Two sibling receipt PRs merged in either order therefore cannot both consume one predecessor's slices: first-parent order resolves which valid candidate entered first, and the later candidate fails its predecessor check. Main rebase/fast-forward histories are interpreted only as their actual verified first-parent commit order; the evaluator never invents past ref-update or PR batching from that topology. Retain the last observed main tip: if it ceases to be an ancestor, or an observed deletion/recreation or rewrite invalidates the anchor/history, the cached result is unresolved. A checkpoint or matching polls cannot prove that no unseen rewind occurred. Declare the observed ancestry/protection assumptions and any unobservable-history coverage limit; no new protection setting is authorized. This is logical serialization over existing Git history, not a general compare-and-swap API or a physical deployment lock.

Malformed history, ambiguous candidates, edited accepted records or missing required evidence halt subsequent acceptance at the last valid prefix. A well-formed stale sibling is instead a recorded loser and does not corrupt that valid prefix. Resumption requires an explicit append-only reconciliation manifest from the existing finalizer, an exact-scope nonauthor review, preserved safe identities/evidence for the invalid observations and last valid prefix, with the explicit privacy exception above rather than public copies or links that re-expose removed material, and an explicitly pinned successor checkpoint/interpretation. It may not silently erase a failure, reconstruct missing history as fact or alter scientific dispositions. This recovery uses the same manifest/receipt record types; it is not a new authority register.

Persist exact as-of evidence, integrate the receipt normally, then reconcile both the accepted fold and current deployed vector before reporting a completed release. Record the observation time/cut; no sequence of polls guarantees that no later deployment occurs.

A losing or out-of-pipeline candidate can be actually served. Record it as observed-live/uncommitted and make incompatible current coverage unverified, even when the Git fold accepted another receipt. A stale or mixed vector cannot clear its current-publication obligations. Git ordering is insufficient for an atomic claim that the accepted bytes are served at the instant of acknowledgment; this plan deliberately makes only exact as-of satisfaction claims, with separately revocable current-live coverage. Later observed deployment, source or disposition changes generate new affected events rather than rewriting historical acknowledgment. Queue acknowledgment means only that the exact version-bound publication obligation was satisfied at the recorded observation; it never promises perpetual current availability or clears separate scientific/review obligations. The pending queue is a generated projection, with no destructive external task-close side effect.

If it cannot, store clearly uncommitted evidence-only observations and keep finalization/acknowledgment blocked; do not quietly weaken the protocol.

## Exact queue consumption and failure rules
The unit consumed is (change ID, affected object version, surface ID/version, verification contract), not the entire mutable queue or a repository HEAD.
- Freeze the intended slice set and source-cut vector
- Verify required publication prerequisites from either a compatible prior verified receipt or this release
- Acknowledge only the exact successful slices; an event remains pending while any required surface is outstanding
- Deferred/excluded slices retain explicit reasons and do not masquerade as publication; they can be dispositioned separately without becoming verified
- Live reachability can be recorded even for a conditional/defective mathematical source, but does not clear its review/readiness obligation
- A failed deployment operation consumes no slices. After successful deployment, partial verification acknowledges only slices whose version-bound contracts and prerequisite closure are satisfied; failed or unverified surfaces and their actual dependents remain pending
- Unrelated successful surfaces need not wait for another packet's long replay
- New changes after freeze remain queued; stale expected head/build/vector requires reconciliation, never overwrite
- An optional broken citation can be a separate link-repair obligation rather than blocking unrelated scientific scope
- No race or successful merge silently removes contrary findings
